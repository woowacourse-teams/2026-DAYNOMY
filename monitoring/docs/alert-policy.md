# DAYNOMY 1차 알림 정책

## 목표

DAYNOMY는 초기 트래픽을 운영하는 2인 팀이므로, 모든 오류를 알리는 대신 사용자가
영향을 받거나 곧 장애로 이어질 가능성이 큰 상태만 알린다. 프론트엔드 브라우저 오류와
성능은 Sentry가 담당하고, 이 정책은 백엔드·EC2·PostgreSQL을 담당한다.

알림 수치는 영구적인 정답이 아니다. 1~2주 운영 데이터를 모은 뒤 실제 정상 범위와
대응 경험을 근거로 조정한다.

## 상태 변화

```text
정상(inactive)
  → 조건 초과
대기(pending)
  → 규칙의 for 시간 동안 계속 초과
장애(firing)
  → group_wait 뒤 최초 Slack 알림
  → 계속 장애면 repeat_interval 뒤 재알림
  → 정상화되면 Slack 복구 알림
```

`for`는 장애를 확정하는 지속 시간이고, `repeat_interval`은 확정된 동일 장애를 다시
알리는 주기다. 두 값은 서로 다른 역할을 한다.

## 현재 알림 기준

| 영역 | 환경 | 조건 | 지속 시간 | 등급 | 선정 이유 |
|---|---|---|---:|---|---|
| 공개 URL | prod | 홈페이지 또는 `/api/news` 접근 실패 | 2분 | critical | 실제 사용자 접근 불가 |
| 공개 URL | dev | 홈페이지 또는 `/api/news` 접근 실패 | 5분 | warning | 개발 중 재시작 소음 허용 |
| 백엔드 수집 | prod | Actuator 수집 실패 | 2분 | critical | 프로세스·Alloy 이상 가능성 |
| 백엔드 수집 | dev | Actuator 수집 실패 | 5분 | warning | 개발 환경 확인용 |
| EC2 | prod | server 또는 DB 호스트 메트릭 없음 | 3분 | critical | EC2·Alloy·네트워크 중단 가능성 |
| EC2 | dev | server 또는 DB 호스트 메트릭 없음 | 5분 | warning | 개발 환경 확인용 |
| HTTP 오류 | prod | 5분 요청 20건 이상, 5xx 5건 이상, 비율 5% 초과 | 추가 2분 | critical | 저트래픽의 오류 1건 오탐 방지 |
| HTTP 지연 | prod | 핵심 API 10분 요청 20건 이상, p95 2초 초과 | 추가 5분 | warning | 사용자 체감 성능 저하 |
| JVM Heap | prod | 90% 초과 | 15분 | warning | 짧은 GC 전후 변동은 제외 |
| DB 풀 | prod | 대기 요청 1개 이상 | 5분 | warning | 커넥션 풀 고갈 조기 감지 |
| PostgreSQL | prod | exporter가 DB 연결 실패 | 2분 | critical | 백엔드 핵심 의존성 중단 |
| PostgreSQL | dev | exporter가 DB 연결 실패 | 5분 | warning | 개발 DB 확인용 |
| 디스크 | dev/prod | 여유 공간 15% 미만 | 10분 | warning | 로그·DB 증가로 인한 장애 예방 |
| TLS | dev/prod | 인증서 만료 14일 미만 | 1시간 | warning | 갱신 대응 시간 확보 |

HTTP 지연 알림에서는 `/api/admin/**`와
`/api/news/{newsId}/portfolio-analysis`를 제외한다. 이 요청들은 OpenAI·공공데이터·S3
등 외부 연동 때문에 정상 상황에서도 오래 걸릴 수 있기 때문이다. 해당 작업은 2차에서
외부 제공자별 지연과 성공률 지표로 분리한다.

## 전송 주기

| 구분 | 최초 묶음 대기 | 변화 확인 | 같은 장애 재알림 |
|---|---:|---:|---:|
| prod critical | 30초 | 5분 | 30분 |
| prod warning | 30초 | 5분 | 2시간 |
| dev warning | 30초 | 5분 | 4시간 |
| TLS 만료 | 30초 | 5분 | 24시간 |

모든 receiver는 `send_resolved: true`로 설정해 복구 알림도 전송한다.

## 1차에서 대시보드만 보는 항목

- EC2 CPU·메모리: 순간 상승이 정상 작업인지 장애인지 초기에는 구분하기 어렵다.
- 요청량: 트래픽 기준선을 파악하기 위한 지표다.
- PostgreSQL 세부 통계: 연결 수·커밋·롤백·캐시 적중률을 먼저 관찰한다.
- GC·스레드: JVM 정상 범위를 파악한 뒤 알림 여부를 결정한다.

대응 방법이 정해지지 않은 지표에는 알림을 만들지 않는다.

## 2차 후보

- OpenAI·공공데이터·S3 요청 성공률과 지연 시간
- 뉴스 생성 작업의 마지막 성공 시각과 실패 횟수
- 종목·주가 동기화 작업의 마지막 성공 시각과 처리 건수
- monitoring EC2 자체의 외부 감시

이 항목은 현재 기본 Micrometer 지표만으로 의미 있게 구분할 수 없으므로 커스텀 지표나
외부 감시가 필요하다.

## 조정 규칙

1. 실제 대응하지 않은 알림이 반복되면 임계값 또는 `for`를 높인다.
2. 장애인데 알림이 늦으면 `for`를 줄이거나 critical로 승격한다.
3. 정상 범위를 최소 1~2주 수집한 뒤 CPU·메모리 등 추가 알림을 결정한다.
4. 임계값 변경 시 변경 이유와 날짜를 이 문서에 기록한다.
