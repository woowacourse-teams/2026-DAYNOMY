# 거래 등록 V1/V2 프로파일링과 동시 요청 비교

## 측정 범위

2026-10-15 로컬 전용 환경에서 거래 등록을 측정했다. V1 거래·스냅샷 코드는
기준 커밋 `0dba10d7`에서 변경하지 않았다. V2의 계산 규칙도 변경하지 않았다.
이번 변경은 프로파일링·반복 실행·분석 도구와 문서다.

회원 50명, 회원당 보유 20종목, 매수 거래 1,000건과 최초 잔고 이력 20건,
과거 스냅샷 131개를 준비했다. 초기 데이터 hash는
`e812854492f34ac082d2b4744211409fc2f33688751e86ebaf488ab277a17143`이다.
이는 운영 사용자 분포를 모사한 자료가 아닌, 날짜·동시성 영향을 비교하는
결정적 합성 데이터다. 가격은 평일마다 1원 증가하며 수수료·세금은 0이다.

macOS arm64·논리 CPU 14개, Java 21.0.12, PostgreSQL 16.15, k6 1.1.0,
Hikari 최대 연결 10개를 사용했다.
부하 발생기·애플리케이션·Docker PostgreSQL은 같은 컴퓨터에서 실행했다.
다른 장비·네트워크·운영 데이터에서 같은 개선 배수가 나온다고 해석하지 않는다.

## 프로파일링 방법

`benchmark.py profile`로 오늘·1개월 전·6개월 전 BUY를 각각 측정했다.
각 경로를 2건 워밍업하고 초기 데이터를 복원한 뒤, VU 1명으로 3건을 실행했다.
JDK JFR profile 설정에서 DB SocketRead의 threshold를 0ms로 설정했다.
스택 깊이는 128로 기록하고 분석 시 실행 샘플은 64프레임까지 사용했다.
프로파일러를 사용한 응답시간은 별도 성능 비교 집계에서 제외한다.

실행 샘플은 API 포트 8496의 처리 스레드만 사용한다. 관리 포트의 샘플은 제외한다.
ExecutionSample은 10ms, NativeMethodSample은 20ms 주기이므로 두 종류의
샘플을 합친 비율을 CPU 사용시간이나 전체 경과시간 비율로 해석하지 않는다.
사전 데이터 검증과 CSRF 획득도 기록 구간에 포함된다.

DB 소켓 읽기 시간은 JDBC가 응답을 기다리는 시간이며 DB 내부 SQL 실행시간과
다르다. GC 정지는 JVM 전체 이벤트다. 샘플·소켓·GC 시간을 단순 합산해
API 전체 시간을 분해할 수 없다.

## 확인한 병목

V1 6개월 전 BUY의 API 처리 스레드 샘플 741개 중 461개에서 Hibernate의
자동 flush 경로, 245개에서 JDBC/통신 경로가 관찰됐다. 거래 이력 계산기의
`replay` 경로에 해당하는 샘플은 1개였다. 이력 계산 비용이 0이라는 의미는 아니다.

주기가 같은 Java 실행 샘플만 분리하면 다음과 같다. 비중은 전체 경과시간이 아닌
해당 종류의 샘플에서 차지하는 비율이다.

| V1 등록 조건 | Java 실행 샘플 | 자동 flush 경로 샘플 | 해당 샘플 비중 |
| --- | ---: | ---: | ---: |
| 1개월 전 | 57 | 49 | 85.96% |
| 6개월 전 | 463 | 434 | 93.74% |

6개월 조건의 NativeMethodSample은 278개 중 244개가 JDBC/통신 경로였다.
오늘과 V2의 짧은 기록은 샘플이 1~3개뿐이라 경로별 비율을 해석하지 않았다.

자동 flush 스택 안에서 엔티티 속성 읽기와 `DirtyHelper.isDirty`·`findDirty`가
관찰됐다. V1은 종가를 조회할 때마다 JPA 조회 경로에 진입하고, 그 과정에서
자동 flush를 위한 변경 감지를 반복한다. 명시적인 날짜별 `saveAndFlush`만이
아니라 **반복 SELECT에 동반되는 ORM 작업**도 병목으로 확인됐다.

같은 3건의 기록에서 V1의 PostgreSQL 내부 SQL 실행시간 합계는 약 1.19초,
DB SocketRead 합계는 약 22.87초였다. V2는 각각 약 0.017초, 0.142초였다.
스냅샷 UPDATE는 양쪽 모두 요청당 131개로, V2가 갱신을 생략한 결과가 아니다.
V1의 지연을 단일 느린 SQL이나 이력 계산 수식만으로 설명하는 것은 부정확하다.

같은 프로파일링 실행의 자원 관측 구간에서 JVM CPU 누적시간은 V1 약 34.97초,
V2 약 0.21초 증가했다. 이는 사전 검증 등을 포함한 JVM 전체 CPU 누적시간으로,
API 한 건의 정확한 CPU 사용시간은 아니다. DB 내부 실행시간 외에 애플리케이션
측 비용이 크다는 별도 관측 근거다.

원본 JFR·분석 JSON·워밍업/시험 로그는 Git에서 제외되는
`.local/results/profile-496-20261015/`에 저장했다. 원본 프로파일은 로컬 전용이며
공유 자료에는 집계한 메서드 이름·샘플·시간만 사용한다.

## V2가 바꾼 부분

V1은 월별 조회가 아니다. 재계산 날짜마다 이력을 조회하고, 종목마다 당일·직전
가격을 개별 조회한다. V2는 정렬된 이력과 기존 대상 스냅샷을 각각 한 번 조회하고,
가격을 **최대 31개 계산 날짜 단위**로 묶어 가져온다. 31일은 달력의 월이 아니며,
가격 기준일 131개인 이번 데이터에서는 종가 일괄 조회가 5회 발생했다.

V2도 날짜마다 보유 상태·평가금액을 계산하고 스냅샷을 갱신한다. HTTP 응답은
전체 갱신을 끝낸 뒤 한 번 반환한다. `saveAll`이나 변경 감지를 JDBC 일괄 UPDATE로
간주하지 않는다. 거래 이력을 한 번만 순회하는 계산 알고리즘 개선은 이번 범위가 아니다.

## JFR을 끈 기간·동시 사용자 비교

매수 1주 등록을 오늘·1개월 전·6개월 전으로 나누고, VU 1·5·10·20·50명에서
각 회원이 응답 직후 다음 요청을 보내도록 3건씩 실행했다. 각 조건을 3회 반복했다.
각 VU는 서로 다른 회원이다. 각 기간·버전을 2건 워밍업하고 매 시험마다 같은 seed를
복원했다. V1/V2는 순차 실행했고 반복 차수마다 선행 버전을 바꿨다.

표의 시간은 정상 종료하고 결과 검증까지 통과한 세 실행의 POST 평균을 평균한 값(ms)이다.

비교하지 않는다. 완료 표기는 정상 응답 확인 건수/계획 건수이며, 중단된 나머지가

### 50명·6개월 전 V1의 중단

해당 V1 조건은 세 번 모두 약 30초에 HTTP 500으로 중단됐다. 서버 로그에서
`HikariPool-1 - Connection is not available, request timed out after 29996ms
(total=10, active=10, idle=0, waiting=24)`가 확인됐다. 클라이언트의 180초
POST 제한이 아닌 서버의 DB 연결 획득 타임아웃이다.

| 반복 | 정상응답 확인/목표 | 클라이언트 종료까지 관측한 연결 타임아웃 증가 | 종료 후 서버 안정화 대기 초 |
| --- | ---: | ---: | ---: |
| 1 | 10/150 | 16 | 36.24 |
| 2 | 10/150 | 26 | 34.22 |
| 3 | 10/150 | 12 | 41.33 |

타임아웃 카운터·SQL·자원 관측은 클라이언트 시험 종료까지의 값이다. 중단 뒤 계속된
서버 작업의 전체 실패 횟수·SQL 합계를 뜻하지 않는다. DB 연결 사용/대기가
연속 3회 0이 된 뒤 다음 seed를 복원했다. 중단 조건의 평균·p95·처리량은
CSV에서도 비워 정상 성능 값으로 취급하지 않았다.

동일한 V2 조건은 세 번 모두 150/150건을 완료하고 전체 과거 스냅샷 검증을 통과했다.

### 결과의 의미와 한계

- 오늘 거래의 개선 폭은 작고, 과거 스냅샷 갱신 범위가 큰 조건에서 차이가 크게 나타났다.
- 모든 정상 종료 시험에서 현재 수량·평균 매입가·실현손익과 대상 회원의 모든 과거 스냅샷이 예상값과 일치했다.
- V2도 연결 대기가 생긴다. 대기를 완전히 없앤 결과로 해석하지 않는다.
- 각 VU의 요청 건수가 정해진 짧은 동시 요청 시험이다. 고정 도착률·장시간 지속 부하·운영 최대 처리량을 검증한 것은 아니다.
- VU 1명은 버전별 각 기간 9개 요청이다. 적은 표본의 p95/p99를 안정적인 지연 지표로 주장하지 않는다.
- 자원 지표의 최대값은 0.5초 간격 관측의 최대값이다. 짧은 피크는 누락될 수 있다.
- 이번 성능 비교의 거래 종류는 BUY다. SELL의 성능 비교로 일반화하지 않는다.
- 단일 날짜 스냅샷 함수를 반복 호출하면서 생긴 DB 왕복·변경 감지가 확인된 개선 대상이다. 현재 V2의 날짜별 이력 재생은 여전히 남아 있다.

반복별 집계는 [CSV](results/496-20261015.csv), 전체 원본은
`.local/results/matrix-buy-496-20261015/`와 각 시험 label 디렉터리에 보존한다.
CSV에는 토큰·키·회원 정보·원본 응답을 포함하지 않는다.

## 검증과 실행 후 상태

Python 단위 테스트 10개, `./gradlew spotlessCheck test`, CSV 90행의 조건·중단
처리 검증을 통과했다. Gradle의 Java 검사·테스트 작업은 기존 통과 결과를 재사용한
UP-TO-DATE 실행이다. 이번 작업에서 Java 비즈니스·테스트 코드는 변경하지 않았다.
90개 시험 모두 자원 지표 수집 오류는 없었다.

90개 중 정상 완료·정합성 검증은 87개, 연결 타임아웃으로 중단된 시험은 V1의
50명·6개월 전 조건 3개다. V2는 계획한 2,322건 모두 정상 응답을 확인했다.
V1은 정상 시험의 1,872건과 중단 시험에서 확인한 30건의 정상 응답이 기록됐다.
중단 뒤 서버 작업이 계속될 수 있으므로 이 숫자를 전체 DB 커밋 건수로 해석하지 않는다.

모든 시험 후 전용 DB를 초기 seed로 복원하고 테스트 JVM·Compose를 정지했다.
원본 결과와 전용 DB 볼륨은 보존했다.
