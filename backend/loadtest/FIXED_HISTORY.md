# 거래 이력 건수를 고정한 진단 (#981)

이 도구는 이력 증가와 RPS 증가를 분리한다. 운영 용량의 장시간 보장이나 실제 사용자 장애를 입증하는 도구는 아니다.
업무 코드 변경 전 개발 서버에서 SQL 실행·전송·JPA 객체 생성·원장 계산 중 어느 경로가 커지는지 확인한다.

## 비교 조건

- 개발 인스턴스 `i-0f2e92d9c7bd8fe06`, `daynomy_dev`, `https://dev.daynomy.com`만 허용한다.
- 기존 배치 종료 및 이전 JVM 자동 종료를 기다린다. 유휴·단일 JVM·예약 작업 격리를 확인하지 못하면 시작하지 않는다.
- JVM 192MiB / SerialGC / C1 / arena2, 공유 메모리 한도1GiB / swap0을 두 버전에 동일하게 유지한다.
- 배포 컨트롤러와 같은 `deploy.lock`을 실험 중 유지하여 보호된 배포와 겹치지 않게 한다.
- 실험 전용 회원600명, 회원별 이력10/100/500건, 국내 종목1개, 오늘 매수1주·100원·수수료/세금0.
- 구간마다 회원당 신규 요청은 정확히1회다. 따라서 **모든 측정 요청 직전** 이력은 H건, 성공 후 H+1건이다. 거래 저장 뒤 실행하는 실제 원장 조회도 H+1건을 읽는다.
- 매 구간 전후 이력 수·현재 수량·평균 매입가·멱등성 기록 수를 DB와 대조한다.
- 전송한 모든 요청이 끝난 뒤 새 이력과 처리 기록을 백업하고, 소유 데이터만 측정 밖에서 복원한다.
- 각 이력 크기에서 워밍업600건을20 RPS로 실행하고 복원한다. 워밍업 수치는 본 측정에서 제외한다.
- 본 측정:20/40/60 RPS × 키 없음/새 키 ×3회.600건 기준 각 구간의 도착 기간은30/15/10초다.
- 최초 총 예정 요청은 워밍업1,800건 + 본 측정32,400건이다. 전송 누락·실패가 발생하면 즉시 행렬을 중단한다.
- 키 있음/없음 순서는 반복마다 바꾼다. 동일 회원의 잠금 경합은 이 실험의 대상이 아니므로 별도 동시성 테스트로 검증한다.
- 드라이버는 같은 개발 인스턴스의 별도 Python 프로세스다. 대상 JVM 할당과 드라이버 할당을 혼동하지 않는다.
- 짧은 구간의 탐색 결과를 지속 가능한 최대 RPS로 표시하지 않는다.

## 실행 전 검증

```sh
python3 -m unittest discover -s backend/loadtest -p 'test_fixed_history_probe.py'
cd backend
HISTORY_COST_PROBE=true ./gradlew test --rerun-tasks --tests '*PortfolioHistoryCostProbeTest'
```

로컬 진단은 폐기 가능한 PostgreSQL Testcontainers에서 실행한다.5회 워밍업 후20회의 중앙값으로
동일 SQL의 JDBC 전체 열 읽기, JPA 엔티티 조회, 원장 재생의 현재 스레드 누적 할당·시간을 비교한다.
EXPLAIN의 DB 실행 시간은 클라이언트 전송·객체화를 포함하지 않으며 단일 실행은 참고값이다.
JDBC/JPA 차이도 프레임워크 전체 비용 차이이며 특정 내부 함수에 전부 귀속하지 않는다.
로컬 수치는 개발 API 성능 수치로 대체할 수 없다.

## 개발 실행

설정 격리와 같은 JAR 전환은 팀의 배포 컨트롤러로 수행하고 기록한다. 이 도구는 배포나 설정 변경을 하지 않는다.
실험 소유 디렉터리에서 두 Python 파일의 SHA256을 확인한 뒤 실행한다.

```sh
python3 fixed-history-probe.py --run \
  --expected-jar-sha VERIFIED_CURRENT_SHA256 \
  --env-file /home/ec2-user/backend/daynomy.env \
  --output NEW_PRIVATE_EXPERIMENT_DIRECTORY
```

토큰은 전용 회원에만10분 유효기간으로 발급하여 메모리에서 갱신한다. 비밀값이나 토큰을 출력·저장하지 않는다.
DB 오류 원문을 출력하지 않는다. 프로파일·산출물은 실험 소유 비공개 디렉터리에 둔다.

## 별도 할당 프로파일

`profiles/history-allocation.jfc`는 환경변수·시스템 속성·JVM 명령행·프로세스 시작 이벤트를 수집하지 않는
최소 설정이다. 실제 서버 사용 전 가짜 환경변수/속성을 주입한 로컬 JVM에서 `jfr print --json` 결과에
표식이 없고 이벤트 종류가 허용 목록 안에 있는지 검사한다. 지연 비교 구간에는 JFR·스레드 덤프를 켜지 않는다.
JFR 할당 샘플의 weight는 추정치다. 정확한 피크 메모리나 전체 객체 수라고 표시하지 않는다.

## 종료 조건

오류·누락·정합성 불일치가 있으면 더 높은 부하를 시작하지 않는다. 개인정보 없는 실패 요약과 소유 데이터 백업을
남기고 정리한다. 원래 예약 설정을 정확히 복원하고 정상 설정의 단일 JVM이 유휴 상태임을 확인한 뒤 서버를 인계한다.
원인이 확인되기 전에는 거래 잠금·멱등성 기록·계산 규칙을 수정하지 않는다.

개발 DB의 기존 `pg_stat_statements`에서 관련 도메인 SQL의 queryId·호출 수·실행 시간·반환 행 수·버퍼·WAL의
전후 누적 차이를 수집한다. 원문 SQL이나 실제 바인딩 값은 저장하지 않고 전역 통계도 초기화하지 않는다.
이 값은 관련 테이블을 참조하는 SQL 집계이며 모든 프로토콜/트랜잭션 제어문의 수를 포함하지 않는다.
개발 PostgreSQL18에서는 `EXPLAIN ... SERIALIZE TEXT`도 별도5회 수집한다.
워밍업 등록 후 복원 전에 H+1건을 읽는 실제 조건으로 실행하며,
이는 결과를 전송 형식으로 바꾸는 비용이며 네트워크 전송은 포함하지 않는다.
근거: [PostgreSQL18 EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html).

할당 프로파일도 시작 직후600건을 워밍업으로 버린 뒤 다음600건만 해석한다.
`results.json`의 `profile-h500` 시작/종료 시각을 `{"start":"...","end":"..."}`로 저장해
`summarize-history-jfr.py ... --window WINDOW_FILE`로 구간을 제한한다.
로컬의 선택형 `HISTORY_LOCAL_JFR=true`는 조회250회 워밍업 후250회 구간을 별도 기록하며
`build/history-jpa-window.json`에 동일 형식의 시각을 남긴다. 로컬 JFR을 개발 API 결과로 표기하지 않는다.

최신 개발 코드의 예약 작업도 확인한다. 리그·시세·메일 분석·지연 시세 정리 등17개 실행 플래그를 임시로 끄고,
Spring Session JDBC의 매분 정리는 `SPRING_SESSION_JDBC_CLEANUP_CRON=-`로 중단한다.
해당 라이브러리4.1.0의 `JdbcIndexedSessionRepository.afterPropertiesSet()`에서 `-`일 때 예약하지 않는 것을 확인했다.
게스트 체험 만료 정리는 매시17분의 상수 cron이므로 변경하지 않고, 각 구간이16~18분 경계에 걸리면
측정 밖에서 대기한다. 스케줄 복원은 실험 소유 설정만 제거하고 원래 설정으로 다시 전환하여 수행한다.

JFR 설정과 기록 경로는 대상 JVM의 실행 UID가 접근 가능한 별도700 디렉터리에 잠시 준비한다.
상위 디렉터리가 root 전용이면 마지막 출력 디렉터리만 chown해도 JVM이 접근할 수 없기 때문이다.
기록 후600 모드로 실험 산출물에 복사하고 임시 경로를 정리한다. 기록은 최대64MiB·10분으로 제한한다.
`--profile-only --histories 100 --rps 20`처럼 이미 안전성이 확인된 이력 크기를 명시할 수 있다.

첫 DB 쓰기 전에 실험 소유 네임스페이스·DB 목적지 지문·최대 회원 수를 별도의 불변 manifest에 남긴다.
이 파일에는 연결 비밀번호나 토큰을 넣지 않는다. 중단 시 결과 JSON이 불완전해도 소유 계정만 확인하여 복구할 수 있다.
