# 배경 및 해결할 문제

DAYNOMY는 경제 뉴스를 수집·분석하여 사용자의 자산 및 포트폴리오와 연결해 제공하는 서비스이다.

프로젝트에서는 다음과 같은 요구사항을 만족할 수 있는 기술 스택이 필요했다.

- 장기간 유지보수가 가능한 기술 스택
- 최신 보안 업데이트와 버그 수정 지원
- 뉴스 수집 및 AI API 호출 등 I/O 중심 작업을 처리할 수 있는 실행 환경
- 사용자, 포트폴리오, 뉴스 등 관계형 데이터를 안정적으로 관리할 수 있는 데이터베이스
- 향후 복잡한 조회 및 데이터 분석 기능을 지원할 수 있는 데이터베이스

이를 만족하기 위해 Java 버전, Spring Boot 버전, 관계형 데이터베이스를 검토했다.

---

# 검토한 대안과 장단점

## 1. Spring Boot 3.5 + Java 17

### 장점

- 충분히 검증된 기술 스택이었다.
- 레퍼런스와 학습 자료가 풍부했다.
- Java 17 역시 LTS 버전으로 안정적인 지원을 제공했다.

### 단점

- Spring Boot 3.5의 OSS 지원이 종료되었다.
- 가까운 시점에 Spring Boot 4로 마이그레이션이 필요했다.
- Java 21의 Virtual Thread를 사용할 수 없었다.

---

## 2. Spring Boot 4 + Java 21 (선택)

### 장점

- 최신 Spring Boot 버전으로 장기적인 유지보수가 가능했다.
- Java 21 LTS를 지원했다.
- Virtual Thread를 활용할 수 있었다.
- 향후 뉴스 수집 및 AI API 호출과 같은 I/O 중심 작업에 적용할 수 있었다.
- 초기부터 최신 기술 스택을 적용하여 마이그레이션 비용을 줄일 수 있었다.

### 단점

- Spring Boot 3.x보다 참고 자료와 운영 사례가 상대적으로 적었다.
- 일부 라이브러리의 호환성을 확인해야 했다.

---

## 3. Spring Boot 4 + Java 25

### 장점

- 최신 LTS 버전이었다.
- 최신 Java 기능을 활용할 수 있었다.

### 단점

- 운영 사례가 충분히 축적되지 않았다.
- 일부 라이브러리의 호환성이 충분히 검증되지 않았다.

---

## 4. MySQL

### 장점

- 사용 사례와 학습 자료가 풍부했다.
- 운영 경험을 가진 개발자가 많았다.

### 단점

- PostgreSQL보다 복잡한 SQL 기능이 상대적으로 제한적이었다.
- 향후 벡터 검색 등 AI 기능 확장에 제약이 있었다.

---

## 5. PostgreSQL (선택)

### 장점

- ACID 기반의 안정적인 트랜잭션을 지원했다.
- JOIN, Window Function, CTE 등 다양한 SQL 기능을 제공했다.
- JSON 타입을 지원했다.
- pgvector 확장을 통한 벡터 검색이 가능했다.

### 단점

- MySQL보다 운영 경험과 학습 자료가 상대적으로 적었다.
- 일부 환경에서 설정이 다소 복잡했다.

# 최종 결정 내용과 선택 이유

프로젝트의 기본 기술 스택으로 다음을 선택했다.

- **Java 21**
- **Spring Boot 4**
- **PostgreSQL**

### Spring Boot 4

Spring Boot 3.5의 OSS 지원이 종료되었기 때문에 신규 프로젝트를 해당 버전으로 시작할 경우 가까운 시점에 업그레이드가 필요했다.

초기부터 Spring Boot 4를 사용하여 향후 마이그레이션 비용을 줄이고 최신 보안 업데이트를 지속적으로 적용하기로 결정했다.

### Java 21

Spring Boot 4에서 지원하는 LTS 버전 중 Java 21을 선택했다.

뉴스 수집, 금융 데이터 조회, AI API 호출 등 외부 API와의 통신이 많은 서비스 특성을 고려했을 때, Java 21에서 정식 지원하는 Virtual Thread를 활용할 가능성을 확보하기 위함이었다.

다만 Virtual Thread가 모든 상황에서 성능을 향상시키는 것은 아니므로 실제 적용 시에는 처리량, 응답 시간, 스레드 사용량 등을 측정하여 효과를 검증하기로 했다.

### PostgreSQL

사용자, 뉴스, 포트폴리오, 자산 변동 이력 등 관계형 데이터를 안정적으로 관리해야 했으며, 향후 뉴스와 자산 데이터를 결합한 분석 기능 구현을 고려했다.

또한 복잡한 JOIN, 집계, Window Function 등을 적극 활용할 가능성이 높았고, 추후 AI 기능 확장 시 pgvector를 이용한 벡터 검색도 고려할 수 있어 PostgreSQL을 선택했다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- 최신 Spring Boot 기반으로 장기적인 유지보수가 가능해졌다.
- Java 21의 Virtual Thread를 활용할 수 있는 기반을 확보했다.
- PostgreSQL의 다양한 SQL 기능을 활용하여 복잡한 데이터 분석 기능을 구현할 수 있게 되었다.
- pgvector를 활용한 AI 기능 확장 가능성을 확보했다.

## 트레이드오프

- Spring Boot 4는 Spring Boot 3.x보다 운영 사례와 참고 자료가 상대적으로 적었다.
- Java 21과 Virtual Thread에 대한 학습 비용이 발생했다.
- PostgreSQL 운영 경험이 부족한 팀원의 학습이 필요했다.
- Virtual Thread를 사용하더라도 DB 커넥션 풀 등의 제약은 그대로 존재하므로 적용 범위를 성능 측정을 통해 결정하기로 했다.
