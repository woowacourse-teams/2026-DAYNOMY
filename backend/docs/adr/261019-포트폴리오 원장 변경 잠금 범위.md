# 포트폴리오 원장 변경 전에 포트폴리오 잠금 획득

- 날짜: 2026-10-19
- 대상: 보유 추가·정정·삭제, V1/V2 거래 등록, 거래 수정·삭제, 일일 스냅샷 생성

## 문제와 재현 근거

포트폴리오의 현재 보유 상태와 과거 스냅샷은 거래·보유 변경 이력을 재생한 결과다.
같은 포트폴리오의 변경이 겹치면 최종 원장과 이 파생 데이터가 일치해야 한다.

기존 거래 수정·삭제는 이력을 조회하고 변경한 뒤 보유 수량을 계산했다.
포트폴리오 잠금은 이후 `refreshSnapshotsFrom`의 스냅샷 저장 과정에서 획득했다.
이미 이력을 읽은 다음 잠그므로, 앞서 읽은 JPA 엔티티나 계산 결과를 최신 상태로
바꾸는 효과는 없었다. 보유 정정·삭제에는 같은 포트폴리오 잠금이 없었고,
V1 등록은 회원 잠금만 먼저 획득하므로 거래 수정·삭제와 공통 보호 범위가 없었다.

`PortfolioConcurrencyAcceptanceTest`에서 실제 HTTP 요청과 PostgreSQL 16으로 재현했다.

1. 종가·매입가가 100원인 종목에 10주 매수 두 건과 보유 수량 20주를 준비한다.
2. 별도 DB 연결이 포트폴리오 행을 잠근다.
3. 첫 거래를 12주로 수정하는 요청을 보내고 DB 잠금 대기를 확인한다.
4. 둘째 거래를 20주로 수정하는 요청을 보내고 두 요청의 잠금 대기를 확인한다.
5. 별도 연결의 잠금을 풀고 두 요청이 완료된 뒤 DB를 새로 조회한다.

기존 코드에서는 두 요청 모두 200을 반환했지만, 원장을 새로 재생한 결과는 32주이고
저장된 보유 수량은 30주였다. 이 테스트가 보유 수량 비교에서 실패하는 것을 수정 전에 확인했다.
단순히 두 스레드를 동시에 시작하는 데 의존하지 않고 `pg_stat_activity`의 실제
잠금 대기를 확인하여 문제가 생기는 요청 중첩을 만든다.

첫 요청이 아직 커밋하지 않았을 때 둘째 요청이 이력을 읽으면 첫 거래의 예전 10주가
영속성 컨텍스트에 남는다. 첫 요청의 커밋 후 다시 쿼리해도 이미 관리 중인 이력 엔티티를
사용할 수 있어, 둘째 요청의 20주와 합쳐 30주로 계산한다.
스냅샷만 직렬화하는 것으로는 원장 변경 전체를 보호할 수 없는 이유다.

## 대안과 결정

| 대안 | 고려 사항 |
|---|---|
| 포트폴리오 비관적 잠금을 읽기 전에 획득 | 기존 스냅샷·V2 등록의 잠금과 공유할 수 있고 DB 스키마·API 변경이 필요 없다. 같은 포트폴리오 변경은 기다려야 한다. |
| 버전 기반 충돌 감지 | 부모 포트폴리오 자체를 수정하지 않는 자식 이력 변경도 충돌로 감지하도록 설계하고, 충돌 응답·재시도 정책을 정해야 한다. |
| Serializable과 재시도 | 격리 수준 변경과 직렬화 실패 재시도 정책까지 검증 범위가 넓어진다. |

기존 `PortfolioRepository.findByIdForUpdate`를 사용해 **원장·보유 상태를 읽기 전에**
포트폴리오 행의 비관적 쓰기 잠금을 획득한다. 커밋·롤백까지 같은 트랜잭션에서 유지한다.

- V1 보유 추가·거래 등록: 회원 잠금 → 기존 포트폴리오 잠금 → 이력·보유 조회 및 변경.
  포트폴리오 최초 생성은 기존 회원 잠금으로 중복 생성을 막는다.
- 보유 정정·삭제, 거래 수정·삭제: 포트폴리오 잠금 → 이력·보유 조회 및 변경.
- V2 거래 등록: 이미 회원 → 포트폴리오 순서로 잠그므로 기존 구현을 유지한다.
- 일일 스냅샷 생성: 이미 포트폴리오를 잠근 뒤 이력을 읽으므로 기존 구현을 유지한다.

회원 잠금까지 필요한 경로는 회원 → 포트폴리오 순서를 유지한다.
포트폴리오만 잠그는 경로에서는 이후 회원 잠금을 추가 획득하지 않는다.
다른 회원의 포트폴리오를 전역 잠금으로 묶지 않는다.

API 형식, 금액 계산, 과거 거래일 검증, DB 스키마, V2의 일괄 조회 방식은 변경하지 않는다.
읽기 전용 조회에 쓰기 잠금을 추가하거나 모든 조회의 일관된 시점 읽기를 보장하는 변경은 포함하지 않는다.

## 회귀 검증

`src/test/java/org/grit/daynomy/portfolio/acceptance/PortfolioConcurrencyAcceptanceTest.java`는
실제 서버와 PostgreSQL Testcontainers를 사용한다.

| 시나리오 | 검증 내용 |
|---|---|
| 서로 다른 거래를 12주·20주로 동시 정정, 10회 반복 | 원장·보유 수량 32주, 평가 스냅샷 3,200원 |
| 거래 정정 + 다른 거래 삭제 | 삭제 후 원장·보유·스냅샷 일치 |
| 거래 정정 + V1/V2 등록 | 두 경로가 같은 포트폴리오 잠금을 공유 |
| V1 매도 + V1/V2 매도 | 20주에서 각 15주 매도 시 한 건만 성공하고, 거절된 거래는 롤백되어 5주 유지 |
| 보유 정정·삭제 + V2 등록 | 현재 원장·보유 일치, 오늘의 변경이 과거 평가를 바꾸지 않음 |
| 거래 정정 + 스냅샷 생성 | 중복 스냅샷 없이 커밋된 원장과 일치 |
| 한 포트폴리오가 잠금 대기 중 다른 회원의 거래 정정 | 다른 회원 요청은 대기 중인 포트폴리오 잠금 해제 전에 완료 |
| 뒤 날짜 스냅샷의 금액 범위 초과 | 거래 정정·보유 변경·앞 날짜 스냅샷 변경 모두 롤백 |

집중 검증 명령:

```sh
cd backend
./gradlew test --tests '*PortfolioConcurrencyAcceptanceTest'
```

전체 필수 검증:

```sh
cd backend
./gradlew spotlessCheck test
```

### 2026-10-20 미국 거래 연동 브랜치 재검증

- `feature/BE/#553`의 수정 전 코드에는 원장 조회 전 포트폴리오 잠금이 빠져 있었다.
  집중 재현 결과 동시성 테스트 20개 중 13개가 실패했다. 동시 정정 10회는 모두
  원장 32주·저장된 보유 30주였으며, 정정과 V1 등록은 27주 대신 25주,

- `SavedPortfolioService`의 보유 정정·삭제, 거래 수정·삭제는 이력·보유 조회 전에
  포트폴리오 잠금을 획득하도록 수정했다. V1 등록도 회원 잠금 뒤 기존 포트폴리오를 잠근다.
  이미 같은 순서로 잠그는 V2 등록과 스냅샷 생성은 변경하지 않았다.
- 기존 동시성 인수 테스트 20개를 수정하거나 완화하지 않고 모두 통과했다.
  `SavedPortfolioServiceTest` 15개와 USD 거래 인수 테스트 1개도 함께 통과했다.
- 거래일 검증 단위 테스트의 잠금 조회 Mock도 보완한 뒤 `./gradlew spotlessCheck test`를
  실행했다. 전체 894개 중 893개 통과, 기존 조건부 테스트 1개 건너뜀, 실패 0개로 완료했다.

## 영향과 한계

동일 포트폴리오의 재계산이 끝날 때까지 다른 변경과 스냅샷 생성은 대기한다.
정합성을 위해 필요한 직렬화지만, 재계산 기간이 길면 대기 시간도 늘어난다.
이번 테스트는 특정 경합과 실패 상황의 정합성 검증이며, 처리량이나 잠금 대기 p95의
개선 실험은 아니다. 낙관적 잠금·Serializable과의 성능 우열을 측정했다고 주장하지 않는다.
이미 존재하는 불일치 데이터의 운영 복구나 배포는 이번 작업에 포함하지 않는다.
