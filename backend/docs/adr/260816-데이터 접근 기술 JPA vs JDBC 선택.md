# 데이터 접근 기술(JPA vs JDBC) 선택 기준을 논의한다

- **관련 이슈**:

# 배경 및 해결할 문제

DAYNOMY는 회원, 포트폴리오, 관심 종목, 뉴스 등 다양한 도메인 데이터를 관리하는 서비스이다.

프로젝트에서는 개발 생산성과 유지보수성을 확보하면서도, 향후 뉴스 수집 및 분석 기능에서 발생할 수 있는 복잡한 조회와 대량 데이터 처리에 대응할 수 있는 데이터 접근 기술이 필요했다.

이를 위해 다음 사항을 중심으로 JPA와 JDBC를 비교·검토했다.

- 프로젝트 요구사항과 데이터 구조에 적합한 기술
- 개발 생산성과 유지보수성
- 복잡한 조회 및 성능 최적화 대응
- 테스트 작성과 트랜잭션 관리
- JPA와 JDBC를 함께 사용하는 방안

---

# 검토한 대안과 장단점

## 1. JDBC를 기본으로 사용

### 장점

- 실행되는 SQL을 직접 제어할 수 있었다.
- 복잡한 JOIN, 집계, 통계 조회에 유리했다.
- 대량 적재(Batch) 작업에서 성능을 세밀하게 제어할 수 있었다.
- 실행 SQL과 쿼리 횟수를 명확하게 파악할 수 있었다.

### 단점

- CRUD SQL을 모두 직접 작성해야 했다.
- 데이터 구조가 변경될 때 수정해야 하는 SQL과 매핑 코드가 많았다.
- 반복 코드가 증가하여 개발 생산성과 유지보수성이 떨어졌다.
- 초기 개발 속도가 상대적으로 느렸다.

---

## 2. JPA를 기본으로 사용 (선택)

### 장점

- CRUD 기능을 빠르게 구현할 수 있었다.
- 반복적인 SQL 작성이 줄어들었다.
- 도메인 중심으로 개발하기 용이했다.
- 데이터 구조 변경 시 수정 범위가 상대적으로 작았다.
- 유지보수성과 개발 생산성이 높았다.

### 단점

- 실행되는 SQL을 놓치기 쉬웠다.
- 연관관계 설정에 따라 N+1 문제가 발생할 수 있었다.
- 대량 적재 시 영속성 컨텍스트와 Batch 설정을 고려해야 했다.
- 복잡한 조회에서는 추가적인 성능 최적화가 필요할 수 있었다.

---

## 3. JPA와 JDBC를 처음부터 함께 사용

### 장점

- 상황에 따라 적절한 기술을 사용할 수 있었다.
- 복잡한 조회와 일반 CRUD를 각각 최적화할 수 있었다.

### 단점

- 기술 선택 기준이 모호해질 수 있었다.
- 동일한 기능이 JPA와 JDBC로 중복 구현될 가능성이 있었다.
- 코드 관리와 유지보수 비용이 증가할 수 있었다.
- 초기 프로젝트 단계에서는 복잡도가 불필요하게 증가했다.

---

# 최종 결정 내용과 선택 이유

프로젝트의 기본 데이터 접근 기술로 **JPA**를 선택했다.

현재 프로젝트는 회원, 포트폴리오, 관심 종목, 뉴스 등 CRUD 기능이 중심이며, 초기 단계이기 때문에 요구사항과 ERD가 자주 변경될 가능성이 높았다.

JPA를 사용하면 반복적인 SQL 작성과 매핑 코드를 줄일 수 있었고, 객체 중심으로 개발할 수 있어 기능 구현 속도와 유지보수성을 높일 수 있다고 판단했다.

검색, 카테고리 필터, 뉴스 저장 등 기본 기능도 우선 JPA로 구현하기로 했다.

다만 JPA가 모든 상황에서 최적의 선택이라고 판단하지는 않았다.

뉴스 대량 적재, 복잡한 집계 및 통계 조회, 대용량 데이터 처리 과정에서 실제 성능 문제가 확인되는 경우에는 해당 기능에 한하여 JDBC 또는 JDBC Batch를 부분적으로 적용하기로 했다.

JDBC의 도입 여부는 예상이 아닌 실제 실행 SQL, 실행 계획, 처리 시간 등 성능 측정 결과를 근거로 결정하기로 했다.

또한 동일한 저장 기능을 JPA와 JDBC로 중복 구현하지 않으며, 같은 트랜잭션에서 동일한 데이터를 두 기술로 동시에 수정하는 방식은 지양하기로 했다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- CRUD 중심 기능을 빠르게 개발할 수 있게 되었다.
- 반복적인 SQL 작성이 줄어 유지보수성이 향상되었다.
- 요구사항과 ERD 변경에 유연하게 대응할 수 있게 되었다.
- 실제 성능 문제가 발생한 영역만 선택적으로 최적화할 수 있는 기준을 마련했다.

## 트레이드오프

- JPA의 동작 원리와 영속성 컨텍스트에 대한 이해가 필요하게 되었다.
- 연관관계 설계가 잘못될 경우 N+1 문제 등이 발생할 수 있다.
- 대량 적재 시 Batch 설정, flush, clear 등의 추가적인 최적화가 필요할 수 있다.
- 복잡한 조회에서는 JPQL만으로 해결하기 어려운 경우가 발생할 수 있으며, 이 경우 JDBC를 별도로 관리해야 한다.
