# 단일 EC2에서 백엔드 두 포트 전환

관련 이슈: [#943](https://github.com/woowacourse-teams/2026-DAYNOMY/issues/943)

상태: 최신 dev에서 재적용·검증 중. 운영 커밋 기준 사전 실험과 구분하며 운영 전환 완료를 뜻하지 않는다.

## Problem

운영 백엔드는 systemd 재시작으로 배포하므로 기존 프로세스 종료부터 새 앱 준비까지
API를 처리할 앱이 없다. 진행 중 요청 보호만으로 새 앱의 기동 공백을 없앨 수 없다.
추가 EC2·로드밸런서 없이 기존 EC2와 Nginx를 사용해야 한다.

## Alternatives

| 방안 | 이 프로젝트에서의 판단 |
|---|---|
| 재시작 + graceful shutdown | 진행 중 HTTP 요청을 마무리하지만 다음 앱의 기동 공백은 남는다. |
| Rolling | 여러 앱을 순차 교체하는 방식이다. 여러 EC2가 필수는 아니지만, 현재 한 앱만 있는 구성에서는 먼저 두 앱을 동시에 수용할 메모리와 라우팅이 필요하다. |
| Canary | 같은 EC2에서도 포트별 트래픽 비율 분배가 가능하다. 두 앱의 메모리뿐 아니라 버전별 오류 관측과 점진적인 비율 조정이 필요하다. 현재 목표인 배포 기동 공백 제거에 비해 운영 범위가 크다. |
| 두 포트 Blue/Green | 기존 앱을 유지한 채 새 앱을 준비하고, 준비 후 Nginx 대상을 한 번 바꾼다. 같은 EC2의 두 포트로 가능하며 두 EC2가 필수는 아니다. 이전 JAR로 다시 준비하고 전환할 수 있다. |

## Action

- blue는 기존 `daynomy.service` / 8080, green은 `daynomy-green.service` / 8082.
- 관리 포트는 8181/8182이며, 기존 수집 주소 127.0.0.1:8081은 Nginx가 활성 앱으로 연결한다.
- 두 JVM에 Xmx128m, C1 컴파일, MALLOC_ARENA_MAX=2를 적용한다.
  두 JVM의 합계 systemd slice는 800MiB, swap은 0이다. 운영 여유 메모리 256MiB를
  보존하며 시작 전 여유가 656MiB 미만이면 새 앱을 시작하지 않는다.
- 준비 상태와 실제 API·슬롯 헤더를 확인한 뒤 Nginx를 reload한다.
  기존 Nginx worker의 요청이 끝나기 전에는 이전 JVM을 종료하지 않는다.
- 예약 배치와 명시적인 시작 배치는 활성 슬롯만 실행한다. Java FileChannel과
  Python lockf가 같은 POSIX 잠금을 공유한다. 실행 중 배치가 끝난 뒤 소유권을 바꾼다.
  잠금/소유권 파일을 읽지 못하면 배치를 실행하지 않는다.
- HTTP 요청의 기존 포트폴리오별 DB 잠금과 계산 규칙은 바꾸지 않는다.
- 스키마 마이그레이션의 추가·변경·삭제가 있으면 자동 배포를 거절한다.
- 후보 JVM에 높은 OOM 점수를 주고 검증 중에는 기존 JVM을 우선 보호한다.
  검증 완료 후 활성 JVM을 보호한다. 메모리 부족 자체를 해결해 주는 설정은 아니다.

## Result와 적용 한계

결과 수치는 `../backend-bluegreen-runbook.md`에 실측과 미검증을 구분해 기록한다.
EC2 자체 장애에 대한 고가용성은 제공하지 않는다. 단일 호스트 파일 잠금이므로
다른 EC2를 추가할 때는 이 소유권 제어를 그대로 사용하면 안 된다.

초기 버전은 예약 배치를 전역 잠금으로 직렬 실행한다. 별도 이메일 스케줄러의 작업도
다른 예약 배치와 기다릴 수 있다. 300초 내 배치 잠금을 얻지 못하면 전환을 중단하고
기존 앱을 유지한다. 외부 수집·이메일 등 모든 운영 배치의 장기 검증을 대체하지 않는다.

첫 설치는 기존의 소유권 제어 없는 앱을 한 번 재시작한다. 이 중단을 숨기지 않고
기준값으로 측정한다. 이후 전환의 관측 실패 0건은 관측 간격보다 짧은 중단까지
없었다는 증거가 아니며, 측정한 API·부하·기간의 결과로만 표현한다.
