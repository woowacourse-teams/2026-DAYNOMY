# 배경 및 해결할 문제

DAYNOMY는 주요 HTTP API에 요청이 몰릴 때 응답 시간, 처리량, 오류율을 측정하고 병목을 찾기 위해 부하 테스트를 진행하려고 한다. 검색, 리그 순위, 포트폴리오 계산, 뉴스 조회 등이 검토 대상이다.

프로젝트에서는 다음과 같은 요구사항을 만족할 필요가 있었다.

- 작은 API 시나리오부터 시작할 수 있도록 구축 부담이 적을 것
- 시나리오와 부하 조건을 코드로 관리하고 같은 조건에서 반복 실행할 수 있을 것
- 응답 시간, 처리량, 오류율을 확인하고 성능 통과 기준을 설정할 수 있을 것
- 기존 GitHub Actions와 Prometheus·Grafana 환경을 활용할 수 있을 것

이를 위해 k6, Apache JMeter, nGrinder, Locust를 검토했다.

---

# 검토한 대안과 장단점

## 1. k6 (선택)

### 장점

- JavaScript로 HTTP 시나리오를 작성하고 Git에서 변경 이력을 관리할 수 있다.
- 별도 관리 서버 없이 CLI로 작은 테스트를 실행할 수 있다.
- `constant-arrival-rate`로 응답 시간과 독립적인 반복 시작률을 설정할 수 있다.
- `threshold`로 성능 통과 기준을 정의할 수 있어 향후 CI 연동에 적합하다.

### 단점

- 팀원이 JavaScript 기반 테스트 스크립트를 작성하고 익혀야 한다.
- 장기 결과 보관과 상세 대시보드에는 별도 연동이 필요하다.
- 큰 규모의 분산 테스트에는 추가 실행 환경이 필요하다.

---

## 2. Apache JMeter

### 장점

- GUI로 시나리오를 구성할 수 있고 다양한 프로토콜을 지원한다.
- CLI 실행과 리포트 생성도 가능하다.

### 단점

- GUI 중심 시나리오가 복잡해지면 변경 내역을 리뷰하고 유지보수하기 어렵다.
- 큰 부하를 만들 때 실행기의 리소스 사용량을 고려해야 한다.

---

## 3. nGrinder

### 장점

- 웹 UI에서 테스트 실행과 결과 공유가 가능하다.
- Controller와 Agent를 통한 분산 실행을 지원한다.

### 단점

- Controller와 Agent를 설치하고 운영해야 한다.
- 현재 필요한 작은 API 시나리오에 비해 초기 운영 부담이 크다.

---

## 4. Locust

### 장점

- Python으로 사용자 행동을 코드화할 수 있다.
- 웹 UI와 분산 실행을 지원한다.

### 단점

- Python 실행 환경과 패키지를 관리해야 한다.
- Python에 익숙하지 않은 팀원에게 학습 비용이 있다.

# 최종 결정 내용과 선택 이유

프로젝트에서는 첫 HTTP API 부하 테스트 도구로 **k6**를 선택하기로 결정했다.

팀은 복잡한 실행 환경을 구축하기보다 작은 API 시나리오를 먼저 작성하고 결과를 분석해야 한다. k6는 별도 관리 서버 없이 CLI로 실행할 수 있고, JavaScript 파일로 시나리오와 부하 조건을 관리할 수 있다. `constant-arrival-rate`로 서버 응답 시간과 독립적인 반복 시작률을 설정하고, `threshold`로 통과 기준을 정의할 수 있다.

JMeter는 GUI가 장점이지만 복잡한 시나리오의 변경 사항을 리뷰하기 어렵다. nGrinder는 웹 대시보드와 분산 실행을 제공하지만 Controller와 Agent 운영 부담이 있다. Locust도 코드 기반 대안이지만 Python 실행 환경이 필요하다. 현재는 k6로 시작하고, 서버와 DB 상태는 기존 Prometheus·Grafana 지표로 함께 확인하는 편이 적합하다.

또한 다음과 같은 원칙을 적용하기로 했다.

- 부하 테스트 시나리오와 실행 조건을 코드로 관리해 결과를 반복 비교할 수 있게 한다.
- 주요 HTTP API의 응답 시간, 처리량, 오류율과 서버·DB 지표를 함께 확인한다.

Discussion에서는 GitHub Actions 자동화가 필요하다는 의견과 개발 환경에서 기준값을 먼저 측정한 뒤 자동화하자는 의견이 모두 나왔다. 따라서 이번 ADR은 **도구 선정**에 한정한다. 향후 초기 측정 결과를 확보하면 대상 API, 부하 크기, p95·오류율 기준치, CI 실행 시점과 환경을 별도로 결정한다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- API 부하 시나리오와 측정 조건을 코드로 재현하고 리뷰할 수 있다.
- 일정한 반복 시작률에서 응답 시간과 오류율 변화를 관찰할 수 있다.
- 기준치가 정해지면 `threshold`의 실행 결과를 CI에 활용할 수 있다.

## 트레이드오프

- 팀이 k6 스크립트 작성 방법을 익혀야 한다.
- 테스트 결과를 장기간 보관하거나 분산 부하를 만들려면 추가 구성이 필요하다.
- 공유 개발 환경의 상태에 따라 측정 결과가 달라질 수 있어 실행 환경과 기준치를 별도로 정해야 한다.
