# V1/V2 거래 등록의 요청 키와 원자적 결과 저장

- 범위: 단건 거래 등록 V1/V2. 보유 정정·거래 수정/삭제·가져오기·프론트 변경 제외.
- 선행 근거: `261019-포트폴리오 원장 변경 잠금 범위.md`의 회원 → 포트폴리오 잠금과 외부 환율 사전 조회 규칙.
- 개발 기준: `edf59f645fb35ebb9a16566b02bd2dbbe609bb9e`, DB V97. 기존 개인 작업 트리의 V90/V91은 배포 코드와 내용이 달라 이 기준에서 변경을 격리했다.

## 문제와 보장

개발 실험에서 같은 키의 순차 2회/동시 4회 요청이 V1/V2 모두 2건/4건으로 등록됐다.
개발 API의 201을 받은 프록시가 하위 응답을 끊은 뒤 재시도하면 서로 다른 거래 ID가 발급됐다.
현재 포트폴리오 잠금은 원장을 직렬화하지만 동일 거래 의도를 식별하지 않는다.

인증된 회원의 `Idempotency-Key`가 같은 단건 거래 등록은 최대 한 번 커밋한다.
키는 V1/V2가 공유한다. 같은 회원·키로 다른 입력을 보내면 409를 반환한다.
다른 키의 같은 내용 거래와 다른 회원의 같은 키는 별도 의도다.
이 보장은 HTTP 실행 자체나 외부 조회가 한 번이라는 뜻이 아니며, 모든 요청의 성공을 보장하지 않는다.

## HTTP 계약

- 선택 헤더 `Idempotency-Key`: ASCII 영문·숫자·`._:-`, 1~128자. 공백·빈 값·초과는 400 `INVALID_IDEMPOTENCY_KEY`.
- 헤더가 없으면 기존 API 동작을 유지한다. 키 없는 재시도의 중복 방지는 보장하지 않는다.
- 성공·완료된 재요청 모두 201이며 최초 `transactionId`, 당시 보유, 당시 손익을 반환한다.
  이후 다른 거래가 생겨도 최초 결과를 반환하므로 최신 보유는 조회 API로 확인한다.
- 같은 키의 다른 입력: 409 `IDEMPOTENCY_KEY_CONFLICT`. 원장 변경 없음.
- 신규 요청의 DB 잠금 대기 한도는 잠금 획득마다 5초다. 초과는 503 `PORTFOLIO_TRANSACTION_BUSY`.
  클라이언트는 같은 키로 제한된 지수 백오프와 지터를 적용해 재시도한다. 총 HTTP 처리 시간을 5초로 보장하지 않는다.
- 인증/권한·CSRF·DTO 검증은 재요청에도 적용된다. 완료된 요청은 외부 환율 장애·거래 삭제 후에도 재실행하지 않는다.
- 실패 응답은 저장하지 않는다. 전체 롤백된 요청의 키는 재사용할 수 있다. 커밋 후 응답 실패라면 기록이 남아 재응답한다.

입력 해시는 종목·매수/매도·거래일·수량·단가·수수료·세금·환율·거래 시각을 포함한다.
숫자의 소수 자릿수 차이(100.0/100.00)는 정규화한다. 생략된 환율(null)과 명시한 1은 서로 다른 입력으로 취급한다.
시각의 생략과 명시도 구분한다. 입력 필드를 추가하면 해시 규칙과 재응답 호환성을 함께 검토한다.

## 저장·잠금·실패 경계

1. 키 검증과 입력 해시 계산 후 커밋된 결과를 조회한다. 있으면 환율 조회 없이 재응답/충돌 처리한다.
2. 신규 요청의 환율을 기존 ADR처럼 트랜잭션 밖에서 준비한다.
3. 쓰기 트랜잭션에서 회원 잠금을 획득하고 요청 기록을 다시 조회한다. 다른 인스턴스가 준비/잠금 대기 중 커밋했을 수 있다.
4. 기록이 없으면 기존 서비스의 원장 → 현재 보유 → 스냅샷 처리를 실행한다. 회원 → 포트폴리오 잠금 순서는 유지한다.
5. 같은 JPA 트랜잭션에 참여하는 JDBC 연결로 최초 응답을 저장하고 함께 커밋한다.

`portfolio_transaction_requests`의 `(member_id, request_key)` PK를 최종 방어선으로 둔다.
회원 잠금이 API 버전과 앱 인스턴스에 독립적인 직렬화 수단이다. 메모리 캐시나 Redis는 도입하지 않는다.
유니크 위반을 잡은 뒤 실패한 PostgreSQL 트랜잭션에서 계속 조회하는 방식은 사용하지 않는다.
응답 직렬화/저장 실패 시 거래까지 롤백한다. 읽을 수 없는 저장 결과는 재실행 대신 오류로 처리한다.

기록은 포트폴리오/거래 삭제에 연쇄 삭제되지 않는다. 삭제한 거래의 늦은 재시도로 재등록되는 일을 막는다.
응답 스키마 버전은 1이며 변경 시 이전 버전 판독을 유지해야 한다.

## 보관과 관측

현재 성공 키에는 자동 TTL/정리를 적용하지 않고 회원 삭제까지 유지한다. 기간 만료로 중복이 허용되는 빈틈을 만들지 않는 선택이다.
회원 FK는 회원 삭제 시 연쇄 삭제한다. 보관 정책을 바꾸려면 재시도 보장 기간과 늦은 요청 정책부터 명세한다.
거래당 응답 한 건이 추가되므로 테이블 크기·증가량을 운영에서 확인해야 한다.

`daynomy.portfolio.transaction.idempotency{outcome=created|replayed|conflict|invalid|busy|failed}` 카운터로 요청 결과를 센다.
회원 ID·키·종목·금액을 메트릭 라벨이나 오류 메시지에 넣지 않는다. created/replayed는 성공 반환에 도달한 요청 수다.

## 검증

`PortfolioIdempotencyAcceptanceTest`는 PostgreSQL과 실제 HTTP로 교차 버전 동시 요청, 최초 결과 재응답,
입력 충돌, 숫자 정규화·시각 구분, 실패 매도/결과 저장 실패의 롤백, 잠금 대기 초과 후 재시도,
거래 삭제 이후 재시도, 회원 격리와 키 없는 클라이언트 호환을 검증한다.
단위 테스트는 완료 결과의 외부 조회 차단, 손상된 결과 재실행 금지, 입력 해시 범위를 검증한다.
기존 동시성·스냅샷·USD 인수 테스트는 완화하지 않고 함께 실행한다.

개발 재검증에서는 원래 실험과 동일하게 전용 회원으로 순차/동시/다른 키/입력 변경/커밋 후 응답 차단을 확인한다.
실험 데이터는 별도 백업 후 대상 회원만 정리한다. 개발 실행 결과와 로컬 테스트 결과는 구분한다.
