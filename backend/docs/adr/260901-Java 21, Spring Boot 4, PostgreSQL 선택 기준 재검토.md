# Java 21, Spring Boot 4, PostgreSQL 선택 기준을 재검토한다

- **관련 이슈**: #137

# 배경 및 해결할 문제

DAYNOMY는 경제 뉴스를 수집·분석하여 사용자의 자산 및 포트폴리오와 연결해 제공하는 서비스이다.

기존에는 [Java 21, Spring Boot 4, PostgreSQL 선택 기준 논의](./260816-Java%2021,%20Spring%20Boot%204,%20PostgreSQL%20선택%20기준%20논의.md)를 통해 기술 스택을 선택했다. 이후 기획이 변경되면서 현재 구현 및 사용 중인 기술 스택을 기준으로 기존 결정을 재검토하고, 변경된 요구사항에 맞는 선택 기준을 새롭게 기록할 필요가 생겼다.

프로젝트에서는 다음과 같은 요구사항을 만족할 수 있는 기술 스택이 필요했다.

- 장기간 유지보수가 가능한 기술 스택
- 최신 보안 업데이트와 버그 수정 지원
- 뉴스 수집 및 AI API 호출 등 I/O 중심 작업을 처리할 수 있는 실행 환경
- 회원, 자산, 관심 자산, 뉴스 및 뉴스 분석 결과 등 관계형 데이터를 안정적으로 관리할 수 있는 데이터베이스
- 뉴스의 부분 검색, 카테고리 필터, 정렬·페이지네이션과 향후 복잡한 조회를 지원할 수 있는 데이터베이스

이를 만족하기 위해 Java 버전, Spring Boot 버전, 관계형 데이터베이스를 다시 검토했다.

관계형 데이터 관리, 데이터 정합성, JOIN·집계·Window Function·CTE와 같은 일반적인 SQL 기능은 MySQL과 PostgreSQL 모두 지원할 수 있는 공통 요구사항으로 보았다. 따라서 데이터베이스는 관계형 데이터 처리 가능 여부보다 현재 사용 중인 환경, 검색 요구사항, 마이그레이션 비용을 중심으로 비교했다.

# 검토한 대안과 장단점

## 1. Spring Boot 3.5 + Java 17

### 장점

- 충분히 검증된 기술 스택이었다.
- 레퍼런스와 학습 자료가 풍부했다.
- Java 17 역시 LTS 버전으로 안정적인 지원을 제공했다.

### 단점

- Spring Boot 3.5의 OSS 지원이 종료되었다.
- 가까운 시점에 Spring Boot 4로 마이그레이션이 필요했다.
- Java 21에서 정식 지원하는 Virtual Thread를 사용할 수 없었다.

---

## 2. Spring Boot 4 + Java 21 (선택)

### 장점

- Spring Boot 4 계열을 사용하여 장기적인 유지보수 기반을 마련할 수 있었다.
- Java 21 LTS를 지원했다.
- Java 21의 Virtual Thread를 도입할 수 있는 기반을 확보할 수 있었다.
- 뉴스 수집 및 AI API 호출과 같은 I/O 중심 작업에 적용 가능성을 확보할 수 있었다.
- 초기부터 선택한 기술 스택을 적용하여 향후 마이그레이션 비용을 줄일 수 있었다.

### 단점

- Spring Boot 3.x보다 참고 자료와 운영 사례가 상대적으로 적었다.
- 일부 라이브러리의 호환성을 확인해야 했다.

---

## 3. Spring Boot 4 + Java 25

### 장점

- 최신 LTS 버전이었다.
- 최신 Java 기능을 활용할 수 있었다.

### 단점

- 운영 사례가 충분히 축적되지 않았다.
- 일부 라이브러리의 호환성이 충분히 검증되지 않았다.
- 현재 프로젝트의 라이브러리와 운영 환경에 대한 추가 검증 및 학습이 필요했다.

---

## 4. MySQL

### 장점

- 사용 사례와 학습 자료가 풍부했다.
- 운영 경험을 가진 개발자가 많았다.
- 현재 DAYNOMY의 관계형 데이터 구조를 충분히 구현할 수 있었다.

### 단점

- 현재 PostgreSQL을 기반으로 JPA, 검색 쿼리 및 일부 핵심 테스트가 구성되어 있어 변경 시 마이그레이션 비용이 발생했다.
- PostgreSQL 전용 인덱스와 운영 스크립트를 다른 방식으로 대체해야 했다.
- 테스트 환경과 데이터베이스 설정을 함께 변경해야 했다.

---

## 5. PostgreSQL (선택)

### 장점

- 현재 백엔드 애플리케이션이 PostgreSQL 드라이버와 Spring Data JPA를 기반으로 구성되어 있었다.
- 운영 환경의 검색 성능 개선을 위해 PostgreSQL의 `pg_trgm` 인덱스를 적용할 수 있는 선택지가 있었다.
- 이미 구성된 PostgreSQL 설정, 테스트 환경 및 운영 스크립트를 활용할 수 있었다.

### 단점

- MySQL보다 팀 내 운영 경험과 학습 자료가 상대적으로 적었다.
- PostgreSQL의 기능과 운영 방식에 대한 학습 비용이 발생했다.

# 최종 결정 내용과 선택 이유

프로젝트의 기본 기술 스택으로 **Java 21, Spring Boot 4, PostgreSQL**을 유지하기로 결정했다.

### Spring Boot 4

Spring Boot 3.5의 OSS 지원이 종료되었기 때문에 신규 프로젝트를 해당 버전으로 시작할 경우 가까운 시점에 업그레이드가 필요했다.

초기부터 Spring Boot 4 계열을 사용하여 향후 메이저 버전 마이그레이션 비용을 줄이고, 지원되는 범위에서 최신 보안 업데이트와 버그 수정을 지속적으로 적용하기로 결정했다.

### Java 21

Spring Boot 4에서 지원하는 LTS 버전 중 Java 21을 선택했다. Java 25도 후보였지만, 프로젝트에 사용하는 라이브러리와 운영 환경의 검증 범위, 팀의 학습 비용을 종합적으로 고려하여 Java 21을 유지하기로 했다.

뉴스 수집, 금융 데이터 조회, AI API 호출 등 외부 API와의 통신이 많은 서비스 특성을 고려했을 때, Java 21에서 정식 지원하는 Virtual Thread를 도입할 수 있는 기반을 확보할 수 있기 때문이다.

현재 구현은 동기식 `RestClient`와 기본 스케줄러 실행 방식을 사용하고 있으므로 Virtual Thread를 실제로 적용한 상태는 아니다. 향후 적용 시에는 처리량, 응답 시간, 스레드 사용량, 외부 API 및 DB 커넥션 풀의 동시성 한계를 측정하여 효과와 적용 범위를 검증하기로 했다.

### PostgreSQL

PostgreSQL은 신규로 도입하는 기술이 아니라 현재 사용 중인 데이터베이스이다. 현재 백엔드 애플리케이션은 PostgreSQL 드라이버와 Spring Data JPA를 사용하도록 구성되어 있으며, 검색 Repository와 핵심 인수 테스트도 PostgreSQL 환경을 기준으로 검증하고 있다.

현재 DAYNOMY는 회원, 자산, 관심 자산, 뉴스, 뉴스 분석 결과 등 서로 연관된 데이터를 관계형 구조로 관리한다. 따라서 데이터 간 관계와 정합성을 관리하기에 관계형 데이터베이스인 PostgreSQL이 적합하다고 판단했다.

또한 검색 기능의 비중이 크지는 않지만 뉴스의 제목·설명·본문 부분 검색, 카테고리 필터, 정렬 및 페이지네이션을 지원해야 한다. 현재 검색 쿼리는 JPA/JPQL의 `LIKE` 기반으로 구현하고, 운영 환경의 검색 성능 개선을 위해 PostgreSQL의 `pg_trgm` 인덱스 적용 스크립트를 별도로 마련했다. 인덱스의 실제 적용 여부와 효과는 `EXPLAIN ANALYZE` 결과를 기준으로 결정하기로 했다.

MySQL 역시 관계형 데이터 관리와 현재 검색 요구사항을 충분히 만족할 수 있다. 다만 MySQL로 변경할 경우 데이터베이스 설정, 테스트 환경, PostgreSQL 전용 인덱스 및 운영 스크립트를 함께 변경해야 한다. 현재 PostgreSQL을 사용하며 축적된 구현과 검증 결과를 고려했을 때, MySQL로 변경했을 때 얻을 수 있는 실질적인 이점보다 마이그레이션에 필요한 비용이 더 크다고 판단했다.

따라서 **관계형 데이터베이스로서의 기본 기능은 양쪽 모두 충족하지만, 변경된 기획과 현재 사용 중인 구현·검증 환경을 기준으로 Java 21, Spring Boot 4, PostgreSQL을 최종 기술 스택으로 유지한다.**

또한 본 ADR은 기존 ADR의 결정을 삭제하거나 수정하는 것이 아니라, 변경된 기획과 현재 사용 중인 기술 스택을 반영하여 기존 결정을 재검토한 결과를 기록한다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- Spring Boot 4 계열을 기반으로 장기적인 유지보수와 후속 업그레이드에 대응할 수 있게 되었다.
- Java 21의 Virtual Thread를 향후 도입할 수 있는 기반을 유지할 수 있게 되었다.
- PostgreSQL을 통해 회원, 자산, 관심 자산, 뉴스, 뉴스 분석 결과 등 서로 연관된 데이터를 관계형 구조로 관리할 수 있게 되었다.
- PostgreSQL의 쿼리로 현재 요구사항에 필요한 뉴스 검색 기능을 구현하고, `pg_trgm` 인덱스는 운영 환경에서 성능을 측정한 뒤 선택적으로 적용할 수 있게 되었다.
- 이미 구성된 JPA와 PostgreSQL 기반의 일부 핵심 테스트를 활용하여 불필요한 데이터베이스 마이그레이션 비용을 줄일 수 있었다.

## 트레이드오프

- Spring Boot 4는 Spring Boot 3.x보다 운영 사례와 참고 자료가 상대적으로 적었다.
- Java 21과 Virtual Thread를 실제 적용할 경우 추가적인 학습과 검증 비용이 발생한다.
- PostgreSQL 운영 경험이 부족한 팀원의 학습이 필요했다.
- Virtual Thread를 도입하더라도 DB 커넥션 풀과 외부 API의 동시성 제한은 그대로 존재하므로 적용 범위를 성능 측정을 통해 결정해야 한다.
- PostgreSQL과 MySQL 모두 현재 요구사항을 충족할 수 있기 때문에, PostgreSQL 선택은 특정 기능의 절대적인 우위보다는 **현재 서비스의 데이터 구조, 검색 요구사항, 현재 사용 중인 구현과 검증 환경을 종합적으로 고려한 결정**이다.
