# Entity와 Domain Object를 분리할 것인지 논의한다

- **날짜**: 2026-08-18
- **관련 이슈**:

# 배경 및 해결할 문제

DAYNOMY는 JPA를 데이터 접근 기술로 사용하기로 결정했으며, Entity를 그대로 Domain Object로 사용할지, 아니면 Entity와 Domain Object를 분리하여 사용할지에 대한 설계 기준이 필요했다.

Entity와 Domain Object를 분리하면 영속성 계층과 도메인 계층을 독립적으로 관리할 수 있지만, 객체 간 변환(Mapping) 코드와 중복 클래스가 증가하는 비용이 발생할 수 있었다.

반대로 Entity와 Domain Object를 함께 사용하면 구조는 단순해지지만, Entity가 단순한 데이터 저장 객체로 사용되어 비즈니스 로직이 Service에 집중될 가능성이 있었다.

따라서 프로젝트 규모와 개발 기간, 유지보수성, 개발 생산성을 고려하여 적절한 설계 방식을 검토했다.

논의 과정에서는 다음 사항을 중심으로 비교했다.

- Entity와 Domain Object를 분리할지 여부
- 객체 간 Mapper를 두는 비용과 효과
- 현재 프로젝트 규모에서 적절한 설계 방식
- 장기적인 유지보수성과 개발 생산성
- 비즈니스 로직을 어느 계층에서 관리할지

---

# 검토한 대안과 장단점

## 1. Entity와 Domain Object를 분리

### 장점

- 비즈니스 로직이 JPA와 같은 영속성 기술에 의존하지 않았다.
- 영속성 계층과 도메인 계층의 책임을 명확하게 분리할 수 있었다.
- 도메인 객체를 데이터베이스와 독립적으로 테스트할 수 있었다.
- 향후 영속성 기술이 변경되더라도 도메인 계층의 영향이 적었다.

### 단점

- Entity와 Domain Object 간의 Mapper가 필요했다.
- 객체 수가 증가하여 구조가 복잡해질 수 있었다.
- 필드가 변경될 때 Entity, Domain Object, Mapper를 함께 수정해야 했다.
- 매핑 과정에서 필드 누락이나 오류가 발생할 가능성이 있었다.
- 현재 프로젝트 규모에서는 분리로 얻는 이점보다 관리 비용이 더 클 수 있었다.

---

## 2. Entity를 Domain Object로 함께 사용 (선택)

### 장점

- 구조가 단순했다.
- Entity와 Domain Object를 변환하는 과정이 필요하지 않았다.
- 개발 속도가 빨랐다.
- 반복적인 Mapper 코드가 발생하지 않았다.
- Spring Boot와 JPA에서 일반적으로 사용하는 구조를 그대로 활용할 수 있었다.

### 단점

- Entity가 단순한 데이터 저장 객체로 사용될 위험이 있었다.
- 비즈니스 로직이 Service 계층으로 집중될 가능성이 있었다.
- Entity의 책임이 커질 수 있었다.
- 프로젝트 규모가 커질수록 역할이 모호해질 가능성이 있었다.

---

# 최종 결정 내용과 선택 이유

현재 프로젝트에서는 **JPA Entity를 Domain Object로 함께 사용하기로 결정했다.**

현재 프로젝트는 CRUD 중심의 기능이 많고, Entity와 Domain Object의 차이도 `id`, `createdAt`, `updatedAt`과 같은 영속성 관련 필드 정도에 한정되어 있었다.

이러한 상황에서 Entity와 Domain Object를 분리하면 Mapper 작성, 객체 간 변환, 필드 변경에 따른 수정 범위 증가 등 관리 비용이 더 크다고 판단했다.

또한 현재 프로젝트에서는 영속성 기술을 변경해야 하는 요구사항이 없으며, Entity와 Domain Object의 구조적 차이도 크지 않아 두 객체를 분리할 필요성이 충분하지 않다고 판단했다.

따라서 개발 생산성과 유지보수성을 고려하여 Entity를 Domain Object로 함께 사용하기로 결정했다.

다만 Entity를 단순한 데이터 저장 객체로 사용하면서 비즈니스 로직이 Service에 집중되는 것을 방지하기 위해 다음 원칙을 함께 적용하기로 했다.

- 공개 Setter 사용을 제한한다.
- 상태 변경은 `changeNickname()`, `withdraw()`와 같은 행위 메서드로 캡슐화한다.
- Service는 Repository 조회, 트랜잭션 관리, 외부 API 호출, 여러 객체 간 흐름을 조율하는 역할만 담당한다.
- `createdAt`, `updatedAt`과 같은 기술적 필드는 공통 상위 클래스 또는 임베디드 객체로 관리한다.
- 불필요한 Getter를 제공하지 않아 Entity의 상태를 외부에서 임의로 변경하지 못하도록 한다.

또한 위 기준은 코드 리뷰를 통해 지속적으로 관리하고, 정적으로 검증 가능한 항목은 ArchUnit 적용을 검토하기로 했다.

프로젝트가 성장하면서 Entity와 Domain Object의 책임이 명확하게 달라지거나, 복잡한 비즈니스 규칙이 증가하는 경우에는 필요한 도메인부터 선택적으로 분리하는 방향을 검토하기로 했다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- Mapper 작성 없이 빠르게 기능을 개발할 수 있게 되었다.
- Entity와 Domain Object 간의 중복 코드를 줄일 수 있게 되었다.
- 객체 구조가 단순해져 팀원 모두가 쉽게 이해할 수 있게 되었다.
- CRUD 중심의 현재 프로젝트에 적합한 개발 생산성을 확보할 수 있게 되었다.
- 향후 필요한 경우 복잡한 도메인만 선택적으로 분리할 수 있는 여지를 남겨두었다.

## 트레이드오프

- Entity가 단순한 데이터 저장 객체로 사용되지 않도록 지속적인 코드 리뷰가 필요하게 되었다.
- 비즈니스 로직이 Service로 이동하지 않도록 팀의 설계 원칙을 지속적으로 유지해야 했다.
- 프로젝트 규모가 커질수록 Entity의 책임이 증가할 가능성이 있었다.
- 복잡한 도메인이 추가될 경우 Entity와 Domain Object를 분리하는 리팩터링이 필요할 수 있었다.
- ArchUnit 등 정적 분석 도구만으로는 모든 객체지향 설계 원칙을 검증하기 어려워 팀의 코드 리뷰 기준이 중요해졌다.
