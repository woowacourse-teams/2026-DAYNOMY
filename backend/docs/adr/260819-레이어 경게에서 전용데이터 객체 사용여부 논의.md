# 레이어 간 데이터 객체 사용 기준 결정

- **날짜**: 2026-08-19
- **관련 이슈**: 

---

# 배경 및 해결할 문제

현재 프로젝트에는 Controller, Service, Domain, Repository 등 레이어 사이에서 데이터를 전달할 때 어떤 객체를 사용할지에 대한 공통 기준이 없습니다.

Entity나 하나의 DTO를 여러 레이어에서 함께 사용하면 초기 구현은 단순하지만, API 또는 데이터베이스 구조의 변경이 다른 레이어까지 전파될 수 있습니다. 반대로 모든 경계마다 전용 객체를 만들면 객체와 변환 코드가 과도하게 증가하여 개발 생산성과 가독성이 떨어질 수 있습니다.

프로젝트에서는 다음과 같은 요구사항을 만족할 필요가 있었습니다.

- 레이어 간 결합도를 최소화할 것
- 불필요한 객체 생성과 변환 코드를 줄일 것
- API 및 DB 구조 변경의 영향을 최소화할 것
- MVP 단계에 적합한 단순한 구조를 유지하면서 확장 가능성을 확보할 것

이를 해결하기 위해 **레이어별 데이터 객체 사용 방식**을 검토했습니다.

---

# 검토한 대안과 장단점

## 1. 모든 레이어에서 동일한 DTO 또는 Entity 사용

### 장점

- 구현이 가장 단순하다.
- 객체 생성과 변환 코드가 거의 없다.
- 초기 개발 속도가 빠르다.

### 단점

- Controller가 Domain과 영속성 구조에 직접 의존한다.
- API나 DB 구조 변경 시 영향 범위가 넓어진다.
- 계층 간 책임이 모호해질 수 있다.

---

## 2. 모든 레이어마다 전용 객체 생성

### 장점

- 각 계층의 역할이 명확하게 분리된다.
- 변경 영향이 최소화된다.
- 재사용성과 테스트 용이성이 높다.

### 단점

- 객체와 Mapper가 과도하게 증가한다.
- 단순한 기능에도 많은 보일러플레이트 코드가 발생한다.
- MVP 단계에서는 유지보수 비용보다 개발 비용이 더 커질 수 있다.

---

## 3. 필요한 경우에만 객체를 분리하는 점진적 방식 (선택)

### 장점

- 단순한 기능은 간결하게 구현할 수 있다.
- 복잡한 기능에는 필요한 만큼만 객체를 분리할 수 있다.
- 유지보수성과 개발 생산성의 균형을 맞출 수 있다.

### 단점

- 객체 분리 기준을 팀 내에서 명확히 정의해야 한다.
- 기능마다 구조가 일부 달라질 수 있다.
- 일관성을 유지하기 위한 코드 리뷰 기준이 필요하다.

---

# 최종 결정 내용과 선택 이유

프로젝트에서는 **필요한 경우에만 데이터 객체를 분리하는 점진적인 구조**를 선택하기로 결정했습니다.

MVP 단계에서는 구조를 지나치게 복잡하게 만들기보다 단순한 개발 흐름을 유지하는 것을 우선합니다. 다만 외부와 내부의 경계는 명확하게 분리하여 변경 영향이 다른 계층으로 전파되지 않도록 합니다.

최종적으로 데이터 객체의 사용 기준은 다음과 같습니다.

```text
Controller
    ↓
Request DTO
    ↓
Service
    ↓
Domain
    ↓
Response DTO
    ↓
Client
```

필요한 경우에는 다음과 같이 Command, Query, Result 객체를 추가합니다.

```text
Controller
    ↓
Request DTO
    ↓
Command / Query
    ↓
Service
    ↓
Result
    ↓
Response DTO
```

Command, Query, Result 객체는 다음과 같은 경우에만 도입합니다.

- API 요청 형식과 Service가 사용하는 데이터의 의미가 다른 경우
- 하나의 기능을 Batch, Scheduler 등 여러 진입점에서 재사용하는 경우
- 여러 Domain의 데이터를 조합해야 하는 경우
- Domain 객체를 그대로 반환하기 어려운 경우
- 변경 영향이 다른 계층으로 전파될 가능성이 큰 경우

또한 다음과 같은 원칙을 적용하기로 했습니다.

- Controller에서는 Request/Response DTO를 사용하며 Entity를 직접 노출하지 않는다.
- 외부 API의 요청·응답 객체는 Infrastructure 레이어 내부에서만 사용하고 내부 객체로 변환한다.
- Command, Query, Result는 모든 기능에 일괄 적용하지 않고 필요한 경우에만 도입한다.
- DTO와 Domain 간 변환은 계층의 경계에서 수행한다.
- 단순 CRUD는 불필요한 객체 생성을 지양하고 간결한 구조를 유지한다.

향후 비즈니스 로직이 복잡해지거나 여러 서비스에서 재사용되는 기능이 증가할 경우에는 Command, Query, Result 및 Domain 분리를 확대하는 방향을 검토하기로 했습니다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- API와 내부 구현의 결합도를 낮출 수 있다.
- 불필요한 객체 생성과 매핑 코드를 줄일 수 있다.
- MVP 단계에서 빠른 개발과 유지보수의 균형을 맞출 수 있다.
- 복잡한 기능은 점진적으로 구조를 확장할 수 있다.

## 트레이드오프

- 기능마다 객체 구조가 일부 달라질 수 있다.
- 객체 분리 기준을 팀원 모두가 동일하게 이해해야 한다.
- 향후 구조 확장 시 일부 리팩터링이 필요할 수 있다.
- 코드 리뷰를 통해 분리 기준이 지속적으로 관리되어야 한다.
