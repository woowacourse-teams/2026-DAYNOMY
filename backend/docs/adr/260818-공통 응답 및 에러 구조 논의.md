# 공통 응답/에러 구조를 논의한다

- **날짜**: 2026-08-18
- **관련 이슈**: #27

---

# 배경 및 해결할 문제

DAYNOMY의 프론트엔드와 백엔드가 API를 주고받는 과정에서 성공 응답과 실패 응답의 구조를 일관되게 정의할 필요가 있었다.

초기에는 성공 여부, HTTP 상태, 메시지, 데이터 등을 모두 응답 본문에 포함하는 공통 응답 구조를 고려했다.

```json
{
  "status": "SUCCESS",
  "httpStatus": 200,
  "message": "뉴스를 조회했습니다.",
  "data": {
    "id": 1,
    "title": "뉴스 제목"
  }
}
```

하지만 HTTP 응답 자체에 이미 성공/실패 여부와 상태 코드가 포함되어 있어, 응답 본문에 `status`, `httpStatus`, `success` 등의 값을 다시 포함하는 것이 중복인지 검토할 필요가 있었다.

또한 동일한 HTTP 상태 코드에서도 에러 원인이 다를 수 있기 때문에 프론트엔드에서 구체적인 실패 원인을 구분할 수 있는 방법도 필요했다.

이를 위해 다음 사항을 중심으로 공통 응답 및 에러 구조를 검토했다.

- 성공/실패 여부를 응답 본문에 포함할지 여부
- HTTP 상태 코드를 응답 본문에 중복해서 포함할지 여부
- 성공과 실패 응답의 구조를 동일하게 유지할지 여부
- 같은 HTTP 상태 코드에서 서로 다른 비즈니스 에러를 구분하는 방법
- 프론트엔드에서 에러 상황별로 분기할 수 있는 구조
- 성공 및 에러 메시지를 어느 계층에서 관리할지

---

# 검토한 대안과 장단점

## 1. `status`, `httpStatus`, `message`, `data`를 공통으로 반환

### 예시

```json
{
  "status": "SUCCESS",
  "httpStatus": 200,
  "message": "뉴스를 조회했습니다.",
  "data": {
    "id": 1,
    "title": "뉴스 제목"
  }
}
```

### 장점

- 성공과 실패 응답이 동일한 구조를 가질 수 있었다.
- 응답 본문만 확인해도 성공 여부와 HTTP 상태를 알 수 있었다.
- 프론트엔드에서 공통 응답 타입을 정의하기 쉬웠다.

### 단점

- HTTP 응답 자체에 이미 상태 코드가 존재해 `httpStatus`가 중복 정보가 되었다.
- `"SUCCESS"`, `"ERROR"`와 같은 문자열 값을 비교해야 했다.
- 같은 HTTP 상태를 가진 서로 다른 에러 원인을 구분하기 어려웠다.
- 성공 응답에서도 실제 데이터와 관련 없는 공통 필드가 계속 포함되었다.

---

## 2. `success` 또는 `isSuccess` boolean 값을 포함

### 예시

```json
{
  "isSuccess": true,
  "code": null,
  "message": "뉴스를 조회했습니다.",
  "data": {
    "id": 1,
    "title": "뉴스 제목"
  }
}
```

### 장점

- boolean 값을 통해 성공 여부를 직관적으로 확인할 수 있었다.
- 문자열 상태 값을 비교하지 않아도 되었다.
- 성공과 실패를 동일한 응답 타입으로 관리할 수 있었다.

### 단점

- HTTP 상태 코드만으로도 성공과 실패를 판단할 수 있어 정보가 중복되었다.
- 성공 응답에서는 `code: null`과 같이 의미 없는 값이 포함되었다.
- 동일한 구조를 유지하기 위해 불필요한 필드를 채워야 했다.
- 응답 데이터가 불필요하게 복잡해졌다.

---

## 3. HTTP 상태 코드로 성공/실패를 판단하고 성공 응답은 데이터만 반환 (선택)

### 성공 응답

```json
{
  "id": 1,
  "title": "뉴스 제목"
}
```

### 실패 응답

```json
{
  "code": "NEWS_NOT_FOUND",
  "message": "해당 뉴스를 찾을 수 없습니다."
}
```

### 장점

- HTTP 프로토콜의 상태 코드를 그대로 활용할 수 있었다.
- `success`, `status`, `httpStatus`와 같은 중복 필드를 제거할 수 있었다.
- 성공 응답은 실제 필요한 데이터만 반환해 구조가 단순해졌다.
- 실패 응답의 `code`를 통해 동일한 HTTP 상태에서도 에러 원인을 구분할 수 있었다.
- 프론트엔드에서 HTTP 상태와 비즈니스 에러 코드를 각각 필요한 용도에 사용할 수 있었다.

### 단점

- 성공과 실패의 응답 구조가 서로 달라졌다.
- 프론트엔드에서 성공 응답과 에러 응답 타입을 별도로 정의해야 했다.
- 에러 코드가 추가되거나 변경될 경우 프론트엔드와 백엔드 간 공유가 필요했다.
- 에러 코드가 많아질수록 별도의 관리 규칙이 필요했다.

# 최종 결정 내용과 선택 이유

성공 여부는 **HTTP 상태 코드**를 기준으로 판단하고, 성공 응답은 필요한 데이터만 반환하며 실패 응답은 `code`와 `message`를 반환하기로 결정했다.

성공 응답에서는 `success`, `status`, `httpStatus` 등의 공통 필드를 추가하지 않고 실제 클라이언트가 필요로 하는 데이터만 반환하기로 했다.

```json
{
  "id": 1,
  "title": "뉴스 제목"
}
```

실패 응답에서는 프론트엔드가 구체적인 에러 원인에 따라 동작을 구분할 수 있도록 비즈니스 에러 코드와 메시지를 반환하기로 했다.

```json
{
  "code": "NEWS_NOT_FOUND",
  "message": "해당 뉴스를 찾을 수 없습니다."
}
```

HTTP 상태 코드는 성공과 실패를 구분하는 역할을 담당하고, `code`는 동일한 HTTP 상태 코드 내에서 구체적인 실패 원인을 구분하는 역할을 담당하도록 책임을 분리했다.

예를 들어 뉴스와 사용자를 찾지 못한 경우 모두 `404 Not Found`를 사용할 수 있지만, 다음과 같이 서로 다른 에러 코드를 통해 프론트엔드에서 상황별 처리가 가능하도록 했다.

```json
{
  "code": "NEWS_NOT_FOUND",
  "message": "해당 뉴스를 찾을 수 없습니다."
}
```

```json
{
  "code": "USER_NOT_FOUND",
  "message": "해당 사용자를 찾을 수 없습니다."
}
```

프론트엔드에서는 Axios의 기본 동작을 활용해 2xx 응답은 정상 흐름에서 처리하고, 4xx 및 5xx 응답은 예외 흐름에서 처리하기로 했다.

```typescript
try {
  const response = await axios.get<News>("/api/news/1");

  return response.data;
} catch (error) {
  if (!axios.isAxiosError<ErrorResponse>(error)) {
    throw error;
  }

  if (!error.response) {
    return;
  }

  const httpStatus = error.response.status;
  const errorCode = error.response.data.code;

  if (httpStatus === 401) {
    // 로그인 처리
  }

  if (errorCode === "NEWS_NOT_FOUND") {
    // 뉴스 없음 처리
  }
}
```

성공 메시지는 프론트엔드에서 관리하고, 백엔드의 `message`는 실패 상황에서 사용자 안내나 디버깅에 필요한 정보로 활용하기로 했다.

입력값 검증 오류처럼 여러 개의 상세 오류 정보가 필요한 경우에는 필요에 따라 `errors`와 같은 추가 필드를 확장할 수 있도록 했다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- HTTP 상태 코드와 응답 본문의 역할이 명확하게 분리되었다.
- 성공 응답에서 불필요한 공통 필드를 제거해 응답 구조가 단순해졌다.
- 동일한 HTTP 상태에서도 에러 코드를 통해 구체적인 실패 원인을 구분할 수 있게 되었다.
- 프론트엔드에서 HTTP 상태와 비즈니스 에러 코드에 따라 필요한 동작을 구분할 수 있게 되었다.
- 백엔드의 공통 예외 처리기를 통해 에러 응답 형식을 일관되게 관리할 수 있게 되었다.

## 트레이드오프

- 성공 응답과 실패 응답의 구조가 서로 달라졌다.
- 프론트엔드에서 정상 응답 타입과 에러 응답 타입을 별도로 관리해야 했다.
- 백엔드에서 에러 코드를 추가하거나 변경할 경우 프론트엔드와 변경 사항을 공유해야 했다.
- 에러 코드가 증가할수록 코드 목록을 체계적으로 관리할 필요가 생겼다.
- 네트워크 오류, 타임아웃, CORS 등 서버의 에러 응답 자체가 없는 경우에는 별도의 예외 처리가 필요했다.
