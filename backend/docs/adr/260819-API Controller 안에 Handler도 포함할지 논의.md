# 테스트 전략 및 테스트 종류별 작성 기준 결정

- **날짜**: 2026-08-19
- **관련 이슈**: 

---

# 배경 및 해결할 문제

현재 프로젝트에는 테스트 종류별 작성 대상과 범위에 대한 공통 기준이 없습니다.

테스트 기준이 명확하지 않으면 중요한 비즈니스 로직에 대한 테스트가 누락되거나, 반대로 동일한 내용을 단위 테스트, 슬라이스 테스트, 통합 테스트에서 반복해서 검증하는 문제가 발생할 수 있습니다. 인간은 불안하면 같은 걸 세 번 확인하는 경향이 있지만, 테스트 코드에서까지 그럴 필요는 없습니다.

프로젝트에서는 다음과 같은 요구사항을 만족할 필요가 있었습니다.

- 중요한 비즈니스 로직과 핵심 사용자 흐름을 안정적으로 검증할 것
- 테스트 종류별 책임을 구분하여 중복 테스트를 최소화할 것
- 운영 환경과 유사한 데이터베이스 환경에서 필요한 동작을 검증할 것
- 외부 API나 Spring Framework 자체 기능처럼 직접 통제하기 어려운 영역을 적절한 방식으로 테스트할 것

이를 해결하기 위해 **단위 테스트, 슬라이스 테스트, API 인수 테스트, 외부 API 연동 테스트의 역할과 적용 기준**을 검토했습니다.

---

# 검토한 대안과 장단점

## 1. 통합 테스트 중심으로 대부분의 기능 검증

### 장점

- 실제 애플리케이션과 유사한 환경에서 테스트할 수 있다.
- 여러 계층이 실제로 연결되어 동작하는지 확인할 수 있다.
- 구현 세부사항보다 전체 기능의 동작을 검증하기 쉽다.

### 단점

- 테스트 실행 속도가 느리다.
- 세부적인 분기와 예외 상황을 모두 검증하기 어렵다.
- 테스트 데이터 준비와 초기화 비용이 크다.
- 실패했을 때 어느 계층에서 문제가 발생했는지 파악하기 어렵다.

---

## 2. 모든 계층과 기능에 세부 테스트 작성

### 장점

- 테스트 커버리지를 높게 유지할 수 있다.
- 각 계층의 동작을 세밀하게 확인할 수 있다.
- 리팩터링 시 회귀 오류를 발견하기 쉽다.

### 단점

- 단순 DTO, 기본 CRUD, 단순 위임 로직까지 테스트가 증가한다.
- 같은 기능을 여러 테스트에서 중복 검증할 가능성이 높다.
- 테스트 유지보수 비용이 실제 구현 비용보다 커질 수 있다.

---

## 3. 테스트 종류별 책임을 나누고 필요한 범위만 검증 (선택)

### 장점

- 세부 로직과 전체 흐름을 목적에 맞는 테스트로 나눌 수 있다.
- 중복 테스트를 줄일 수 있다.
- 테스트 실행 속도와 신뢰성의 균형을 맞출 수 있다.
- 운영 환경과 유사한 PostgreSQL 기반 검증이 가능하다.

### 단점

- 어떤 테스트를 작성할지 판단하는 기준이 필요하다.
- 테스트 종류가 여러 개이므로 팀원 간 용어와 역할을 공유해야 한다.
- 테스트 대상에 따라 Mock, Testcontainers, RestAssured 등 여러 도구를 사용해야 한다.

---

# 최종 결정 내용과 선택 이유

프로젝트에서는 **테스트 종류별 책임을 명확하게 나누고, 각 기능의 특성에 따라 필요한 테스트만 작성하는 전략**을 선택하기로 결정했습니다.

모든 기능을 통합 테스트 하나로 검증하거나 모든 계층에 동일한 수준의 테스트를 작성하지 않습니다.

세부 비즈니스 로직은 빠른 단위 테스트로 검증하고, Controller와 Repository의 기술적인 경계는 슬라이스 테스트로 확인합니다. 사용자 관점에서 중요한 API는 실제 HTTP 요청부터 데이터베이스까지 연결되는 인수 테스트로 검증합니다.

기본적인 테스트 구조는 다음과 같습니다.

```text
Domain · Service
        ↓
    단위 테스트

Controller
        ↓
@WebMvcTest + MockMvc

복잡한 Repository Query
        ↓
@DataJpaTest
        +
PostgreSQL Testcontainers

핵심 API 흐름
        ↓
@SpringBootTest
        +
RestAssured
        +
PostgreSQL Testcontainers
```

## 1. 단위 테스트

Spring Context를 실행하지 않고 하나의 객체나 기능을 외부 의존성과 분리하여 검증합니다.

### 작성 대상

- Domain의 비즈니스 규칙
- Domain의 상태 변경
- Service의 정상 및 예외 분기
- 계산 및 변환 로직
- 별도의 로직이 존재하는 Mapper와 Utility

Service의 Repository나 외부 API Client 등은 Mock으로 대체합니다.

반대로 다음과 같이 별도의 로직이 없는 코드는 테스트하지 않습니다.

```text
단순 getter
단순 DTO
Repository 호출 후 그대로 반환하는 코드
Spring Data JPA 기본 CRUD 자체
```

DTO 내부에 별도의 검증이나 변환 로직이 존재한다면 해당 로직은 테스트합니다.

---

## 2. Controller 슬라이스 테스트

`@WebMvcTest`와 `MockMvc`를 사용하여 Spring MVC와 Controller 영역을 검증합니다.

Service는 Mock으로 대체하여 Controller의 HTTP 경계에 집중합니다.

### 작성 대상

- URL과 HTTP Method
- PathVariable, RequestParam, RequestBody 변환
- Bean Validation
- HTTP Status
- 정상 응답 Body
- 예외 발생 시 에러 코드 및 응답 형식
- Controller가 Service에 전달하는 값

단순히 Controller가 Service를 호출한다는 사실 자체보다 **HTTP 요청을 내부 값으로 올바르게 변환하고 적절한 응답을 생성하는지**를 중심으로 검증합니다.

---

## 3. Repository 슬라이스 테스트

`@DataJpaTest`와 PostgreSQL Testcontainers를 사용하여 Repository와 실제 PostgreSQL의 연동을 검증합니다.

운영 환경과 다른 H2를 사용하는 대신 PostgreSQL을 사용하여 DBMS 차이로 발생할 수 있는 문제를 줄입니다.

다만 Spring Data JPA의 기본 CRUD와 단순한 필드 매핑은 별도로 테스트하지 않습니다.

다음처럼 쿼리 자체의 동작을 확인할 필요가 있는 경우에만 Repository 테스트를 작성합니다.

- 직접 작성한 `@Query`
- JPQL
- Native Query
- 조건 조합이 복잡한 파생 쿼리
- Join이나 집계가 포함된 쿼리
- 중복 제거가 중요한 쿼리
- 정렬 및 페이징 경계값이 중요한 쿼리
- PostgreSQL 전용 기능을 사용하는 쿼리

단순한 Repository 조회는 API 인수 테스트에서 실제 DB까지 연결하여 확인할 수 있으므로 동일한 내용을 다시 테스트하지 않습니다.

---

## 4. API 인수 테스트

`@SpringBootTest(webEnvironment = RANDOM_PORT)`와 RestAssured, PostgreSQL Testcontainers를 사용합니다.

실제 HTTP 요청을 시작점으로 Controller부터 데이터베이스까지 연결되는 전체 흐름을 검증합니다.

```text
HTTP Request
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
PostgreSQL Testcontainers
    ↓
HTTP Response
```

API 인수 테스트에서는 모든 입력 조합이나 예외를 반복해서 검증하지 않고 사용자 관점에서 중요한 대표 시나리오를 검증합니다.

예를 들어 다음과 같은 기능이 대상이 됩니다.

- 뉴스 목록 조회
- 뉴스 상세 조회
- 뉴스 검색
- 시장 분석 결과 조회
- 인증·인가가 필요한 핵심 API

세부적인 Validation이나 에러 응답 형식은 Controller 슬라이스 테스트에서 검증하고, API 인수 테스트에서는 **전체 계층이 실제로 연결되어 핵심 요구사항을 만족하는지**를 확인합니다.

트랜잭션, 이벤트, 배치처럼 API 인수 테스트에서 확인하기 어려운 내부 동작이 있는 경우에만 별도의 통합 테스트를 추가합니다.

---

## 5. 외부 API 연동 테스트

뉴스, OAuth, AI API 등 외부 서비스 연동은 실제 외부 서버를 호출하지 않고 MockWebServer를 사용합니다.

다음과 같은 상황을 검증합니다.

- 정상 응답
- HTTP 오류 응답
- 타임아웃
- 잘못된 응답 Body
- 응답 파싱 실패
- 외부 API 오류에 대한 내부 예외 변환

자동화 테스트에서 실제 외부 API를 호출하면 네트워크 상태나 외부 서비스 상태에 따라 테스트 결과가 달라질 수 있으므로 제외합니다.

실제 API와의 연결 확인이 필요한 경우에는 개발 환경에서 별도로 검증합니다.

---

## 6. 테스트 용어 구분

프로젝트에서는 테스트의 실행 범위에 따라 다음과 같이 용어를 구분합니다.

```text
단위 테스트
→ Spring 없이 하나의 객체나 기능을 독립적으로 검증

슬라이스 테스트
→ Spring Context 중 특정 기술 영역만 실행

@WebMvcTest
→ Controller / MVC 영역

@DataJpaTest
→ Repository / JPA 영역

통합 테스트
→ 둘 이상의 실제 구성요소가 연결되어 협력하는지 검증

API 인수 테스트
→ 실제 HTTP 요청을 시작점으로
   사용자 관점의 API 요구사항을 전체 흐름에서 검증
```

`@DataJpaTest`는 JPA 영역만 실행한다는 측면에서는 슬라이스 테스트이며 Repository, JPA, 실제 DB가 함께 동작한다는 측면에서는 제한된 범위의 통합 테스트 성격도 가집니다.

본 프로젝트에서는 테스트의 실행 범위를 명확하게 표현하기 위해 **Repository 슬라이스 테스트**라는 용어를 사용합니다.

---

또한 다음과 같은 원칙을 적용하기로 했습니다.

- Domain과 Service의 비즈니스 로직은 단위 테스트로 검증한다.
- Controller의 HTTP 요청·응답 경계는 `@WebMvcTest`로 검증한다.
- Repository는 쿼리 자체의 검증 가치가 있을 때만 테스트한다.
- Repository 테스트는 실제 운영 DB와 동일한 PostgreSQL Testcontainers를 사용한다.
- 핵심 API의 정상 통과 흐름은 `@SpringBootTest + RestAssured`로 검증한다.
- 외부 API는 MockWebServer를 사용하여 정상 및 장애 상황을 재현한다.
- 단순 DTO, getter, Spring Data JPA 기본 CRUD는 테스트하지 않는다.
- 같은 내용을 여러 종류의 테스트에서 반복해서 검증하지 않는다.

향후 트랜잭션, 이벤트, 배치 처리 등 복잡한 내부 동작이 증가하거나 사용자 핵심 흐름이 확대될 경우 해당 기능에 필요한 통합 테스트와 API 인수 테스트를 추가하기로 했습니다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- 각 테스트의 목적과 작성 대상이 명확해진다.
- 동일한 기능을 여러 테스트에서 반복 검증하는 문제를 줄일 수 있다.
- 단위 테스트를 통해 세부 비즈니스 로직을 빠르게 검증할 수 있다.
- PostgreSQL Testcontainers를 사용하여 운영 환경과 DB 차이에서 발생하는 문제를 줄일 수 있다.
- 핵심 API는 실제 HTTP 요청부터 DB까지 연결하여 높은 신뢰도로 검증할 수 있다.

## 트레이드오프

- MockMvc, Testcontainers, RestAssured, MockWebServer 등 여러 테스트 도구를 관리해야 한다.
- Testcontainers와 Spring Context를 사용하는 테스트는 단위 테스트보다 실행 시간이 길다.
- 어떤 기능을 어느 테스트에서 검증할지 팀원 간 지속적인 기준 공유가 필요하다.
- 모든 코드를 테스트하지 않기 때문에 테스트하지 않을 영역을 적절하게 판단해야 한다.
