# 배경 및 해결할 문제

현재 프로젝트에는 어떤 상황에서 어떤 레벨의 로그를 남길지에 대한 공통 기준이 없습니다.

로그를 일관된 기준 없이 작성하면 운영 중 장애 원인을 추적하기 어렵고, 반대로 모든 정보를 기록하면 불필요한 로그가 과도하게 쌓여 필요한 정보를 찾기 어려워질 수 있습니다. 또한 민감한 정보가 로그에 포함될 경우 보안상의 문제가 발생할 수 있습니다.

프로젝트에서는 다음과 같은 요구사항을 만족할 필요가 있었습니다.

- 운영 중 장애 원인을 빠르게 추적할 수 있을 것
- 불필요한 로그를 최소화하여 로그의 가독성을 유지할 것
- 민감한 정보가 로그에 기록되지 않도록 할 것
- 향후 로그 수집 및 모니터링 환경으로 확장할 수 있을 것

이를 해결하기 위해 **로그 레벨과 작성 기준, 로그에 포함할 정보 및 출력 형식**을 검토했습니다.

---

# 검토한 대안과 장단점

## 1. 모든 실행 과정에 상세 로그를 기록

### 장점

- 문제 발생 시 모든 실행 흐름을 확인할 수 있다.
- 개발 단계에서 디버깅이 쉽다.
- 장애 분석 시 추가 정보가 부족하지 않다.

### 단점

- 로그 양이 급격히 증가한다.
- 운영 환경에서 필요한 로그를 찾기 어렵다.
- 저장 비용과 성능 부담이 증가한다.

---

## 2. 장애 추적에 필요한 주요 로그만 기록 (선택)

### 장점

- 운영 중 필요한 로그를 빠르게 확인할 수 있다.
- 로그 양을 적절한 수준으로 유지할 수 있다.
- 장애 분석과 운영 모니터링에 적합하다.

### 단점

- 개발 중에는 추가 DEBUG 로그가 필요할 수 있다.
- 로그 작성 기준을 팀 내에서 지속적으로 관리해야 한다.
- 필요한 로그가 누락되지 않도록 코드 리뷰가 필요하다.

---

## 3. 최소한의 ERROR 로그만 기록

### 장점

- 로그 관리가 매우 단순하다.
- 저장 공간을 거의 사용하지 않는다.

### 단점

- 장애 발생 이전의 흐름을 확인하기 어렵다.
- 원인 분석에 필요한 정보가 부족하다.
- 운영 모니터링에 활용하기 어렵다.

# 최종 결정 내용과 선택 이유

프로젝트에서는 **운영 중 주요 흐름과 장애 원인을 추적하는 데 필요한 로그만 기록하는 정책**을 선택하기로 결정했습니다.

MVP 단계에서는 운영에 필요한 핵심 정보만 기록하여 로그의 가독성을 유지하고, 추후 로그 수집 및 모니터링 환경이 추가되더라도 그대로 활용할 수 있도록 구조화된 로그를 사용합니다.

로그 레벨은 다음과 같이 구분합니다.

```text
DEBUG : 개발 환경에서 필요한 실행 흐름과 내부 데이터

INFO : 주요 비즈니스 작업 완료 및 운영적으로 의미 있는 이벤트

WARN : 복구 가능하거나 확인이 필요한 상황
       (외부 API 재시도, 일부 데이터 누락 등)

ERROR : 요청 처리 실패, 외부 API 최종 실패,
        DB 오류, 예상하지 못한 시스템 예외
```

HTTP 요청은 Filter 또는 Interceptor에서 공통으로 기록합니다.

```text
requestId
traceId
HTTP Method
Request URI
HTTP Status
Duration(ms)
```

requestId는 개별 요청을 식별하는 용도로 사용하고, traceId는 하나의 요청에서 발생하는 외부 API 호출이나 비동기 작업까지 포함한 전체 실행 흐름을 연결하는 용도로 사용합니다.

비즈니스 로그는 운영 중 추적이 필요한 주요 작업만 기록합니다.

```text
DEBUG AI 분석 시작
requestId=req-123
traceId=trace-456
newsId=13

INFO AI 분석 완료
requestId=req-123
traceId=trace-456
newsId=13
duration=1800ms
```

예외 로그는 동일한 예외를 여러 계층에서 중복 기록하지 않습니다.

- 예상 가능한 비즈니스 예외는 별도 로그 없이 처리합니다.
- 확인이 필요한 상황은 WARN으로 기록합니다.
- 예상하지 못한 시스템 예외는 최종 처리 위치에서 Stack Trace와 함께 ERROR로 기록합니다.

외부 API 호출은 API 이름, 응답 상태, 처리 시간, 재시도 횟수 등을 기록하며, API Key나 Authorization Header, 전체 요청·응답 Body 등 민감한 정보는 기록하지 않습니다.

또한 다음과 같은 원칙을 적용하기로 했습니다.

- 운영 환경에서는 INFO 이상만 출력하고 DEBUG는 개발 환경에서만 사용한다.
- HTTP 요청에는 requestId와 traceId를 포함하여 로그를 연결한다.
- Request/Response Body와 민감한 정보는 기본적으로 기록하지 않는다.
- 동일한 예외는 한 번만 기록하며 Stack Trace도 최종 처리 위치에서만 출력한다.
- 로그는 JSON 형태의 구조화된 로그를 사용하여 검색과 분석이 가능하도록 한다.

향후 중앙 로그 수집 시스템이나 분산 추적 도구를 도입할 경우에는 현재의 requestId, traceId 기반 구조를 그대로 활용하고, 호출 횟수나 평균 응답 시간 등 지속적으로 집계해야 하는 정보는 로그가 아닌 메트릭으로 관리하기로 했습니다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- 운영 중 장애 원인을 빠르게 추적할 수 있다.
- 로그의 양을 적절하게 유지하여 필요한 정보를 쉽게 찾을 수 있다.
- 민감한 정보 노출 위험을 줄일 수 있다.
- 향후 중앙 로그 수집 및 모니터링 환경으로 확장하기 쉽다.

## 트레이드오프

- 개발 과정에서는 추가적인 DEBUG 로그가 필요할 수 있다.
- 로그 작성 기준을 팀원 모두가 동일하게 이해해야 한다.
- 필요한 로그가 누락되지 않도록 지속적인 코드 리뷰가 필요하다.
- 구조화된 로그를 위한 초기 설정과 관리 비용이 일부 발생한다.
