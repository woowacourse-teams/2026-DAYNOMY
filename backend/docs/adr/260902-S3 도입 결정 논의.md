# 뉴스 이미지 저장 및 전송을 위해 S3 도입을 선택한다

- **날짜**: 2026-09-02
- **관련 이슈**: [Discussion #142](https://github.com/woowacourse-teams/2026-DAYNOMY/discussions/142)

---

# 배경 및 해결할 문제

OpenAI가 생성한 뉴스 이미지를 Base64 문자열로 변환하여 PostgreSQL의 `image_url` 컬럼에 저장하고 있었다. 뉴스 목록 API도 이미지 URL이 아니라 Base64 데이터 전체를 응답에 포함했다.

운영 환경에서 뉴스 10건을 조회한 결과 API 응답 크기는 약 13.52MB였고, 이미지 한 장의 Base64 문자열은 약 1.1~1.5MB였다. 서버 응답 시작 시간은 약 0.1초였지만, 네트워크 환경에 따른 예상 다운로드 시간은 다음과 같았다.

- 20Mbps 환경: 약 5.28초
- 10Mbps 환경: 약 10.56초
- 5Mbps 환경: 약 21.13초

따라서 서버의 처리 속도보다 큰 Base64 데이터를 매번 내려받고, 브라우저가 JSON을 파싱한 뒤 이미지를 디코딩하는 과정이 주요 성능 문제라고 판단했다. 또한 이미지가 API 응답에 포함되어 있어 이미지 지연 로딩, 브라우저 HTTP 캐시, 이미지별 독립 요청 및 CDN 캐시를 활용하기 어려웠다.

프로젝트에서는 다음과 같은 요구사항을 만족할 필요가 있었다.

- 뉴스 목록의 모든 썸네일을 유지하면서 API 응답에서 Base64 데이터를 제거해야 한다.
- 이미지 저장소를 데이터베이스와 애플리케이션 서버의 생명주기로부터 분리해야 한다.
- 브라우저 캐시와 이미지 지연 로딩을 활용할 수 있어야 한다.
- 현재 AWS 기반 운영 환경과 자연스럽게 연동할 수 있어야 한다.
- 서버에 장기 Access Key를 저장하지 않아야 한다.
- 현재 서비스 규모에 불필요한 운영 복잡도를 추가하지 않아야 한다.

이를 해결하기 위해 현재 방식 유지 및 최적화, EC2 디스크 저장, Amazon S3, Cloudflare R2, Cloudinary, Supabase Storage, Google Cloud Storage와 Azure Blob Storage를 검토했다.

# 검토한 대안과 장단점

## 1. Base64 저장 방식 유지 및 최적화

이미지를 Base64 문자열로 데이터베이스에 저장하는 현재 구조를 유지하면서 이미지 해상도 축소, 목록 API에서 이미지 제외, HTTP 응답 압축, API 캐시 등을 적용하는 방식이다.

### 장점

- 새로운 외부 저장 서비스를 도입하지 않아도 된다.
- 현재 배포 구조를 유지할 수 있다.
- 다른 대안보다 구현 범위가 작다.

### 단점

- 이미지 데이터가 계속 데이터베이스에 저장되어 조회와 백업 부담이 증가한다.
- API 응답 크기 문제를 근본적으로 해결하기 어렵다.
- 브라우저가 이미지를 독립적으로 캐시하기 어렵다.
- 이미지 지연 로딩과 CDN 캐시를 활용하기 어렵다.

---

## 2. EC2 디스크에 이미지 저장

이미지를 현재 운영 중인 EC2 인스턴스의 디스크에 저장하고 Nginx를 통해 제공하는 방식이다.

### 장점

- 새로운 클라우드 서비스를 추가하지 않아도 된다.
- 현재 인프라를 활용할 수 있어 초기 구현이 단순하다.
- Nginx를 이용하여 이미지 캐시 정책을 적용할 수 있다.
- 별도의 객체 저장소 비용이 발생하지 않는다.

### 단점

- 이미지가 특정 EC2 인스턴스의 생명주기에 종속된다.
- EC2 장애 또는 서버 교체 시 이미지가 유실될 수 있다.
- 이미지 백업과 디스크 용량을 직접 관리해야 한다.
- 서버를 여러 대로 확장할 경우 이미지 동기화 문제가 발생한다.
- API 서버와 이미지 서버가 디스크 및 네트워크 자원을 공유한다.

---

## 3. Amazon S3에서 이미지 직접 제공 (선택)

OpenAI가 생성한 Base64 이미지를 백엔드에서 WebP 바이트로 디코딩하여 S3에 저장하고, 데이터베이스와 API에는 S3 이미지 URL만 저장하고 반환하는 방식이다.

### 장점

- 이미지 데이터를 데이터베이스와 API 응답에서 분리할 수 있다.
- 이미지 저장소가 EC2 인스턴스의 생명주기와 분리된다.
- EC2 교체와 서버 확장 시 이미지 이전이나 동기화가 필요하지 않다.
- 브라우저 캐시와 이미지 지연 로딩을 활용할 수 있다.
- 현재 AWS EC2 운영 환경과 자연스럽게 연동할 수 있다.
- EC2 Instance Profile Role을 사용하면 장기 Access Key를 서버에 저장하지 않아도 된다.
- 필요한 시점에 CloudFront를 추가할 수 있다.

### 단점

- 저장 용량, 요청 횟수 및 데이터 전송량에 따라 비용이 발생한다.
- S3 버킷, Bucket Policy 및 IAM Role을 설정하고 관리해야 한다.
- 공개 URL을 사용하는 경우 S3 공개 접근 정책을 검토해야 한다.
- 이미지 리사이징이 필요해지면 별도의 처리 방식이 필요하다.
- S3 직접 전송 성능을 운영 환경에서 확인해야 한다.

---

## 4. Amazon S3와 CloudFront 사용

이미지를 S3에 저장하고 CloudFront CDN을 통해 제공하는 방식이다.

### 장점

- 사용자와 가까운 엣지 서버에서 이미지를 제공할 수 있다.
- 반복되는 이미지 요청이 S3까지 전달되는 횟수를 줄일 수 있다.
- S3 버킷을 비공개로 유지하면서 OAC를 통해 접근할 수 있다.
- 이미지 전용 도메인과 CDN 캐시 정책을 적용하기 쉽다.
- 해외 사용자 증가에 대응하기 유리하다.

### 단점

- CloudFront 배포와 OAC를 추가로 구성해야 한다.
- 캐시 정책, 배포 및 무효화에 대한 운영 관리가 필요하다.
- 현재 국내 사용자와 초기 트래픽 규모에서는 효과가 크지 않을 수 있다.
- S3 이미지 응답 속도가 실제 병목이라는 측정 결과가 없다.
- CloudFront 요청과 데이터 전송에 따른 추가 비용이 발생할 수 있다.

---

## 5. Cloudflare R2와 CDN 사용

이미지를 Cloudflare R2에 저장하고 Cloudflare 네트워크를 통해 제공하는 방식이다.

### 장점

- S3 호환 API를 지원한다.
- 인터넷 데이터 전송 비용이 무료다.
- Presigned URL을 지원한다.
- Cloudflare CDN 및 사용자 정의 도메인과 연결하기 쉽다.

### 단점

- EC2와 이미지 저장소의 운영 플랫폼이 분리된다.
- EC2 Instance Profile Role을 사용할 수 없어 별도의 API Token을 관리해야 한다.
- S3와 모든 기능이 동일하지 않다.
- 팀에 AWS보다 익숙하지 않아 학습 및 운영 비용이 발생한다.

---

## 6. Cloudinary 사용

Cloudinary에 이미지를 저장하고 이미지 최적화와 CDN 제공까지 맡기는 방식이다.

### 장점

- 이미지 저장소와 CDN을 함께 제공한다.
- URL을 이용해 이미지 크기와 품질을 조정할 수 있다.
- WebP와 AVIF 등의 이미지 형식 최적화가 쉽다.
- 별도의 썸네일 생성 로직을 줄일 수 있다.

### 단점

- 저장 공간, 이미지 변환 횟수 및 전송량에 따라 비용이 발생한다.
- 트래픽이 증가하면 객체 저장소보다 비용이 커질 수 있다.
- Cloudinary의 URL과 이미지 변환 방식에 대한 의존성이 생긴다.
- 현재 이미지는 이미 저화질 WebP로 생성되고 있어 동적 변환의 필요성이 크지 않다.
- AWS 환경과 별도로 새로운 플랫폼을 관리해야 한다.

# 최종 결정 내용과 선택 이유

프로젝트에서는 초기 이미지 저장 및 전송 구조로 **Amazon S3 직접 전송 방식**을 선택하기로 결정했다.

OpenAI가 생성한 Base64 이미지를 백엔드에서 WebP 바이트로 디코딩하여 S3에 업로드하고, 데이터베이스와 API에는 Base64 데이터 대신 S3 이미지 URL을 저장하고 반환한다.

```text
OpenAI 이미지 생성
→ 백엔드에서 Base64를 WebP 바이트로 디코딩
→ S3에 WebP 이미지 업로드
→ 데이터베이스에 S3 이미지 URL 저장
→ API에서 Base64 대신 이미지 URL 반환
→ 브라우저가 필요한 이미지를 개별 요청
```

S3를 선택한 가장 큰 이유는 이미지 저장소를 데이터베이스 및 애플리케이션 서버의 생명주기와 분리할 수 있기 때문이다.

EC2 디스크에 이미지를 저장하면 초기 구현은 단순하지만, 서버 장애나 교체 시 이미지 이전과 백업이 필요하다. 서버를 여러 대로 확장하면 인스턴스 간 이미지 동기화 문제도 발생한다. S3를 사용하면 EC2가 교체되거나 여러 대로 확장되더라도 이미지 데이터를 별도로 이전하거나 동기화하지 않아도 된다.

현재 운영 환경도 AWS EC2이므로 다른 플랫폼을 추가하는 것보다 권한과 운영 환경을 일관되게 관리할 수 있다. EC2 Instance Profile Role을 사용하면 장기 Access Key를 서버에 저장하지 않고 필요한 S3 권한만 부여할 수 있다.

CloudFront는 초기 구성에서 제외한다. 현재 목표는 CDN 도입 자체가 아니라 뉴스 목록 API에서 Base64 이미지 데이터를 제거하여 응답 크기를 줄이는 것이다. 사용자가 대부분 국내에 있고 S3 서울 리전을 사용하며, 초기 트래픽과 이미지 요청량도 크지 않다.

또한 S3 이미지 응답 속도가 실제 성능 병목이라는 측정 결과가 없으므로 CloudFront와 OAC에 따른 설정 및 운영 복잡도를 먼저 추가하지 않기로 했다. S3 적용 후 실제 응답 속도와 트래픽을 측정하고 필요한 경우 CloudFront를 추가한다.

또한 다음과 같은 원칙을 적용하기로 했다.

- 이미지는 WebP 형식으로 S3에 저장한다.
- 데이터베이스와 API에는 Base64가 아닌 이미지 URL을 저장하고 반환한다.
- S3 객체는 덮어쓰지 않도록 고유한 경로를 사용한다.
- 이미지가 변경되면 새로운 객체 경로를 생성한다.
- S3 객체에는 `Content-Type: image/webp`를 설정한다.
- 고유한 파일명을 사용하는 이미지에는 `Cache-Control: public, max-age=31536000, immutable`을 적용한다.
- 뉴스 목록의 모든 썸네일 표시는 유지한다.
- 뉴스 카드 이미지에는 `loading="lazy"`와 `decoding="async"`를 적용한다.
- 첫 화면의 주요 배너와 뉴스 상세 대표 이미지에는 Lazy Loading을 적용하지 않는다.
- Instance Profile Role에는 지정된 S3 경로에 대한 최소 권한만 부여한다.

기존 Base64 이미지도 순차적으로 S3에 이전하고 데이터베이스의 `image_url`을 S3 URL로 변경한다. 이전 과정에서 S3 업로드가 실패하면 기존 데이터를 변경하지 않는다.

향후 다음 조건 중 하나가 발생할 경우 CloudFront 도입을 검토하기로 했다.

- S3 이미지의 TTFB가 LCP에 유의미한 영향을 준다.
- 이미지 요청량 또는 데이터 전송 비용이 증가한다.
- 해외 사용자가 증가한다.
- S3에 직접 전달되는 요청을 줄여야 한다.
- 조직 정책상 S3 버킷을 비공개로 유지해야 한다.
- 이미지 전용 도메인이 필요하다.

동적 이미지 리사이징, AVIF 변환 및 목록 가상화는 실제 성능 측정에서 추가 개선이 필요하다고 확인될 때 별도로 검토한다.

# 결정에 따른 영향 및 트레이드오프

## 긍정적인 영향

- 뉴스 목록 API에서 Base64 이미지가 제거되어 응답 크기가 감소한다.
- 브라우저가 이미지를 JSON과 독립적으로 요청하고 캐시할 수 있다.
- 뉴스 카드 이미지에 지연 로딩을 적용할 수 있다.
- 이미지 저장 공간이 PostgreSQL에서 분리되어 데이터베이스 조회와 백업 부담이 감소한다.
- 이미지 저장소가 EC2의 생명주기와 분리된다.
- EC2 교체와 서버 수평 확장 시 이미지 이전 및 동기화가 필요하지 않다.
- 실제 성능 측정 결과에 따라 CloudFront를 단계적으로 도입할 수 있다.
- Instance Profile Role을 사용하여 장기 Access Key 노출 위험을 줄일 수 있다.

## 트레이드오프

- S3 저장 공간, 요청 횟수 및 데이터 전송량에 따른 비용이 발생한다.
- S3 버킷, IAM Role, Bucket Policy와 캐시 정책을 관리해야 한다.
- 공개 S3 URL을 사용하려면 버킷 공개 접근 정책을 검토해야 한다.
- 기존 Base64 이미지를 S3로 이전하는 작업이 필요하다.
- S3 업로드와 데이터베이스 저장 사이의 정합성을 처리해야 한다.
- 뉴스 저장이 실패하면 이미 업로드된 S3 객체를 정리해야 한다.
- CloudFront를 사용하지 않으므로 이미지 요청이 S3에 직접 전달된다.
- 해외 사용자 또는 트래픽이 증가하면 응답 속도와 전송 비용을 다시 검토해야 한다.
- 추가 이미지 최적화가 필요하면 별도의 처리 구조를 도입해야 한다.
