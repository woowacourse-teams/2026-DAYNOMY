# PMF 설문 연동 계약 — FE #805 / 별도 BE 이슈

이 문서는 FE #805에서 사용하는 **신규 API 계약 제안**이다. 기존 백엔드에는 아직 이 API가 없다. 별도 BE 이슈에서 구현·배포한 뒤 실제 통합 검증이 필요하다. 일반 피드백 API나 분석 도구로 설문 응답을 우회 전송하지 않는다.

## 승인된 동작

- 중앙 팝업에서 고정 PMF 문항에 답하고, 서버 저장 성공 후 선택 서술형 질문을 표시한다.
- PMF 문항: `이 제품을 더 이상 쓸 수 없다면 어떻겠습니까?`
- 선택지와 순서: `매우 실망` → `약간 실망` → `실망하지 않음` → `더 이상 쓰지 않음`.
- 추가 질문: `그렇게 답하신 가장 큰 이유는 무엇인가요? (선택)` — 공백 제외 1~500자. 건너뛰기·닫기는 첫 응답을 취소하지 않는다.
- **설문 노출 대상과 공식 PMF 집계 대상을 분리한다.** 일반 사용자에게도 노출하되, 응답 시점 기준 최근 2주 안에 포트폴리오 분석 버튼을 누른 팀 밖 사용자만 공식 PMF 결과에 포함한다. 나머지 응답은 별도로 집계한다. 분석 성공 여부를 버튼 클릭 기준으로 바꾸어 해석하지 않는다.
- 기존 팀원 제외 정책을 그대로 적용하고, 대상 판정과 집계 그룹은 서버에서 확정한다. 클라이언트가 보낸 활성 여부를 신뢰하지 않는다. 로그인하지 않은 사용자를 제외한다는 의미는 아니다.
- 프론트 노출 위치는 실제 서비스의 포트폴리오 `/` 화면이다. 첫 방문 소개·로그인·관리자·팀원 도메인에서는 표시하지 않으며 다른 대화상자가 열려 있으면 닫힌 뒤 표시한다.
- `나중에`·닫기는 같은 탭 방문에서 재노출하지 않는다. 키는 설문/계정별로 구분하고 응답 본문은 브라우저 저장소에 남기지 않는다. 첫 응답 후에는 서버의 중복 응답 판정이 브라우저·기기 간 재노출을 막는다.
- 응답이나 서술형 내용은 GA4/PostHog 이벤트·URL·로그로 보내지 않는다.
- 계정 전환·화면 이탈 시 조회와 저장 요청을 중단하고 이전 화면의 늦은 응답은 무시한다. 요청 중단은 서버에서 이미 저장한 응답을 취소한다는 의미가 아니므로, 기응답 조회와 서버 중복 방지는 여전히 필요하다.

## API

기존의 JSON 응답, 쿠키 인증/세션, CSRF 발급(`/api/auth/csrf`) 규칙을 따른다. 게스트는 BE에서 부여한 익명 세션 식별자를 사용하며, 사용자 식별값을 요청 본문으로 받지 않는다.

### GET `/api/pmf-surveys/current`

활성 설문과 **팝업 노출 가능 여부**를 반환한다. `eligible`은 공식 PMF 집계 그룹과 다르다.

```json
{ "surveyId": 805, "eligible": true, "responseId": null }
```

- 예시 `805`는 설문 ID의 예시일 뿐, 이슈 번호를 서버 ID로 고정할 필요는 없다. 모든 ID는 양의 안전 정수다.
- 이미 답했으면 실제 `responseId`를 반환한다. 프론트는 추가 의견 미작성 상태라도 첫 문항을 다시 묻지 않는다.
- 활성 설문이 없으면 `204 No Content`를 반환한다.
- FE는 로딩·실패·잘못된 응답·401/403/404 상태에서 팝업을 표시하지 않는다. 기존 포트폴리오는 정상 이용할 수 있다.
- 대상 판정은 응답 저장 시점에도 재확인한다. 첫 조회 당시 미응답이었다는 이유만으로 중복 저장을 허용하지 않는다.

### POST `/api/pmf-surveys/{surveyId}/responses`

```json
{ "answer": "VERY_DISAPPOINTED" }
```

| 코드                    | 표시 문구         |
| ----------------------- | ----------------- |
| `VERY_DISAPPOINTED`     | 매우 실망         |
| `SOMEWHAT_DISAPPOINTED` | 약간 실망         |
| `NOT_DISAPPOINTED`      | 실망하지 않음     |
| `NO_LONGER_USING`       | 더 이상 쓰지 않음 |

성공 응답: `201 Created` 또는 재시도에 대한 `200 OK`, 본문 `{ "id": 21 }`.

- 설문/응답자당 한 응답을 보장한다. 네트워크 응답 유실·더블 클릭·여러 탭의 재시도에도 기존 응답을 반환하고 중복 집계하지 않는다. 이미 저장한 답변을 재시도로 덮어쓰지 않는다.
- 서버에서 응답 시각, 모집 경로 `IN_APP`, 팀원 제외 여부, 최근 2주 내 핵심 행동 여부와 그 판정 근거를 저장한다. 기준은 포트폴리오 분석 버튼 클릭이며 기존 `start_portfolio_analysis` 이벤트·서버 분석 요청 기록과의 대응을 BE에서 확인한다. 기록이 없어 확인할 수 없는 사용자를 임의로 ‘미사용’으로 분류하지 말고 확인 불가 상태로 구분한다.
- 기본 응답을 먼저 커밋한다. 추가 의견이 오지 않더라도 응답자 수와 선택지별 인원에 포함한다.

### PATCH `/api/pmf-surveys/{surveyId}/responses/{responseId}/reason`

```json
{ "reason": "내 자산과 관련된 소식을 볼 수 있어서요." }
```

성공 응답: `204 No Content`.

- 공백을 정리한 1~500자만 허용한다. 기존 설문 응답과 연결하고 본인 소유 여부를 확인한다. 다른 사용자 응답 수정은 거절한다.
- 같은 응답에 재시도해도 추가 응답을 생성하지 않는다.
- 건너뛰기에는 별도 요청을 보내지 않으며 추가 의견은 미작성 상태로 남긴다.
- 추가 의견 저장 실패 시 기존 PMF 응답은 유지한다. FE는 입력을 유지하고 재시도/건너뛰기를 허용한다.

- [ ] 활성 설문·노출 대상 여부·기응답 조회 API 구현
- [ ] 고정 PMF 선택 응답 저장 및 설문/응답자 단위 중복 방지

- [ ] 일반 응답과 공식 PMF 집계 그룹 분리: 응답 시점 최근 2주 분석 버튼 클릭 여부와 판정 근거 저장
- [ ] 기존 팀원 제외 적용 및 게스트 식별·수집 범위 확인
- [ ] 응답 시각·모집 경로 저장, 응답자 수·선택지별 인원·그룹별 결과 조회 수단 마련
- [ ] 대상·중복·권한·추가 의견 실패 독립성·미확인 이력 테스트와 명세 확정

## 프론트 검증

- `npm run dev -- --host 127.0.0.1 --port 5178` 후 `/pmf-survey-demo.html`에서 실제 서버 전송 없이 두 단계 흐름을 확인한다. 별도 개발 문서에서만 fetch를 대체하며 실제 앱 진입점에는 모의 응답을 넣지 않는다.
- `?fail=answer` / `?fail=reason`은 각각 해당 단계의 첫 저장 실패를 재현한다. 새로고침 후 다시 표시하려면 해당 로컬 미리보기 탭의 `daynomy:pmf-survey:v1:805:guest:dismissed` 세션 키를 지우거나 새 브라우저 세션을 쓴다.
- BE 배포 전 정상 앱에서 설문이 보이지 않는 것은 의도된 동작이다. 미배포 API를 성공으로 처리하거나 로컬 저장만으로 ‘응답이 저장되었어요’를 표시하지 않는다.
