# 프론트엔드 CI/CD 성능 기록

이슈: [#767](https://github.com/woowacourse-teams/2026-DAYNOMY/issues/767)

## 변경 범위

- PR CI: 변경 파일 조회 후 앱 검사와 Docker 배포 검증을 별도 러너에서 병렬 실행한다.
  `Frontend checks`는 두 검사의 성공을 확인한다. 프론트 변경이 없으면 두 검사가
  건너뛰어진 경우에만 통과하며, 변경 조회 실패·검사 실패·취소는 통과시키지 않는다.
- CD: 포맷·린트·타입 검사·테스트·환경별 빌드를 한 job에서 수행하고 Docker 배포
  검증과 병렬 실행한다. 의존성은 한 번 설치하고 타입 검사 결과도 같은 작업 디렉터리에서
  재사용한다. 두 job이 성공해야 이미지 발행·배포가 시작된다. 빌드 결과는 같은 실행의
  아티팩트 ID로 전달하며, 내려받은 HTML의 환경·커밋과 이미지의 버전·커밋을 확인한다.
  PR의 다른 커밋에서 실행한 검사 결과를 재사용하지 않는다.
- E2E: CI의 worker 수를 1개에서 2개로 늘리고, 실행 시간이 몰린
  `portfolio-ledger.e2e.ts`의 독립 테스트만 파일 안에서도 병렬로 실행한다.
  테스트별 API mock·브라우저 격리, 실패 시 스크린샷·trace는 유지한다.
- 로컬 전체 검증에서 발견한 거래 원장 테스트의 타이밍 오류를 수정한다. 모달이
  사라지는 것과 effect 정리에서 스크롤 잠금이 복원되는 것을 함께 기다린다.
  기존 검증 조건·제한 시간과 앱 코드는 유지한다.
- 배포 테스트는 응답을 열린 상태로 유지하고 전환·롤백 후 슬롯 재사용 차단을
  확인한 다음 응답을 완료시킨다. 고정 전송 시간을 기다리지 않으며, 전체 응답 본문과
  연속 HTML·기존 자산 접근을 검사한다. 테스트 포트는 프록시와 같은 Docker 네트워크에서 고른다.
- 컨테이너 시작 유예 구간은 최대 10초, 검사 간격은 1초로 두고 정상 판정 후에는
  기존 30초 간격을 유지한다. 실제 배포·롤백 절차와 이미지 재사용·태그, 캐시 정책은 유지한다.

## 변경 전 GitHub Actions 측정

2026-11-02에 확인한 최근 성공 실행 중 프론트 검사를 실제 수행한 CI 3회와
`dev` CD 3회를 사용했다. 서로 다른 커밋이므로 추세를 파악하는 기준이며,
동일 커밋 반복 실험이나 변경 후 실측값은 아니다.

전체 시간은 실행의 `createdAt`부터 `updatedAt`, 최초 대기는 첫 성공 job의
`startedAt`까지, job 시간은 각 job의 `startedAt`부터 `completedAt`까지다.
전체 시간에는 러너 대기·job 사이 대기·완료 처리 시간이 포함된다.

| 구분    | 실행                                                                                      | 전체 시간 | 최초 대기 | 성공 job 시간 합계 |
| ------- | ----------------------------------------------------------------------------------------- | --------- | --------- | ------------------ |
| CI      | [41396309427](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41396309427) | 7분 42초  | 3초       | 7분 39초           |
| CI      | [41391913253](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41391913253) | 6분 17초  | 4초       | 6분 13초           |
| CI      | [41386374031](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41386374031) | 7분 7초   | 4초       | 7분 2초            |
| 개발 CD | [41394625775](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41394625775) | 6분 5초   | 7초       | 5분 54초           |
| 개발 CD | [41360788295](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41360788295) | 5분 45초  | 7초       | 5분 31초           |
| 개발 CD | [41025668589](https://github.com/woowacourse-teams/2026-DAYNOMY/actions/runs/41025668589) | 5분 58초  | 8초       | 5분 44초           |

| 중앙값           | CI       | 개발 CD       |
| ---------------- | -------- | ------------- |
| 전체 시간        | 7분 7초  | 5분 58초      |
| Docker 배포 검증 | 2분 31초 | 2분 32초      |
| 일반 테스트      | 58초     | 53초          |
| E2E              | 2분 22초 | 실행하지 않음 |

CI 러너는 `ubuntu-latest`, CD 빌드 러너는 `ubuntu-24.04-arm`이다.
두 워크플로 모두 lockfile 기준 npm 다운로드 캐시를 사용한다. 위 표본의
캐시 적중 여부는 확인하지 않았으므로 캐시 개선 효과로 해석하지 않는다.

병렬화하면 CI에서는 배포 검증과 앱 검사 시간이 겹치고, CD에서는 배포 검증과
일반 검사·빌드 시간이 겹친다. 아티팩트 전송과 job별 러너 대기가 추가되므로
겹친 시간 전체를 실제 단축 시간으로 계산하지 않는다.

## 로컬 E2E 비교

macOS ARM64, Node 22.23.2에서 같은 프로덕션 빌드와 테스트 67개를 사용했다.
worker 1개와 2개를 번갈아 각각 3회 실행했고, 여섯 실행 모두 재시도 없이
67개가 통과했다. 시간은 명령 시작부터 종료까지이며 preview 서버 준비도 포함한다.

```bash
CI=true npx playwright test --workers=1 --reporter=list
CI=true npx playwright test --workers=2 --reporter=list
```

| worker 수 | 1회      | 2회      | 3회      | 중앙값   |
| --------- | -------- | -------- | -------- | -------- |
| 1개       | 167.51초 | 236.23초 | 218.20초 | 218.20초 |
| 2개       | 137.02초 | 158.95초 | 122.97초 | 137.02초 |

이 표본의 중앙값은 약 37% 감소했다. 공유 개발 장비의 부하를 통제하지 못해 편차가
있으며, GitHub 러너의 결과나 전체 CI/CD 단축률로 해석하지 않는다.
이 측정은 worker 수만 변경했던 1차 개선의 기록이다. 이후 거래 원장 파일 내부에
[테스트 단위 병렬 실행](https://playwright.dev/docs/test-parallel)을 추가한 결과는 아래에 구분한다.

| 설정                                       | 1회     | 2회     | 3회     | 중앙값  |
| ------------------------------------------ | ------- | ------- | ------- | ------- |
| worker 2개 + 거래 원장 파일 내부 병렬 실행 | 67.81초 | 61.13초 | 67.14초 | 67.14초 |

같은 빌드와 테스트 67개가 재시도 없이 세 번 모두 통과했다. worker 수만 늘린
앞선 표본의 중앙값 137.02초보다 약 51% 짧았지만, 같은 부하에서 교차 측정한 결과는 아니다.
이 측정 전에 Docker 테스트와 함께 실행한 첫 시도에서는 10개가 실패했고,
시간 초과·외부 폰트 연결 끊김·CSS 로딩 오류가 관측됐다. 위 표는 Docker 검증 종료 후
E2E만 실행한 세 번의 결과다. 실패한 실행은 성공 시간 통계에서 제외했으며,
테스트 조건·제한 시간·재시도 설정은 변경하지 않았다.

## 시작 상태 검사와 배포 테스트

실제 앱 이미지로 준비 완료까지 걸린 시간을 측정했다. 변경 전 기본 설정은 1회,
변경 후 Dockerfile은 3회 실행했다. Docker Engine 27.3.1의 로컬 결과다.

| 설정                    | 실행 시간              | 중앙값  |
| ----------------------- | ---------------------- | ------- |
| 기존 30초 검사 간격     | 30.92초                | 30.92초 |
| 시작 구간 1초 검사 간격 | 1.77초, 1.66초, 1.87초 | 1.77초  |

실제 HTTP 응답·HTML 캐시·해시 자산·소개 페이지도 확인했다. 서버가 준비되지 않는
컨테이너는 정상으로 판정되지 않았다. 시작 유예 구간 이후의 30초 검사 간격은 유지한다.
이 설정은 [Docker Engine 25 이상](https://docs.docker.com/reference/dockerfile/#healthcheck)이
필요하며 실제 개발·운영 호스트 버전은 아직 확인하지 않았다.

배포 통합 테스트는 변경 전 1회 188.79초, 최종 변경 후 3회 150.48초·162.25초·207.29초로
모두 통과했다. 변경 후 중앙값은 162.25초다. 공유 장비 부하와 표본 수가 달라
전체 CI/CD의 단축률로 환산하지 않는다. 고정 전송 대기를 제거하면서 전환·롤백 후
기존 요청이 남은 슬롯의 재사용 차단을 명시적으로 검사했다. 임시 복사본에서 이 보호
로직을 제거했을 때 테스트가 실패하는 것도 확인했다.

## 로컬 검증

- 포맷·린트·타입 검사와 프로덕션 빌드 통과.
- 최종 `npm test`에서 단위 테스트 99개, 서버 테스트 7개, UI 테스트 714개 통과.
  1차 검증의 기본 병렬 실행에서는 기존 UI 테스트 2개가 5초 제한에 걸려
  `npm run test:ui -- --maxWorkers=2`로 확인했으며, 최종 검증은 기본 설정으로도
  통과했다. 테스트 제한 시간은 변경하지 않았다.
- Docker 배포 통합 검사의 무중단 전환·롤백·진행 중 요청·해시 자산 보존 검증 통과.
- `Frontend checks`의 실제 shell 조건에 변경 여부·선행 job 결과 192개 조합을
  넣어 실패·취소·예상치 못한 건너뛰기 차단을 확인했다. CD의 검사·빌드와 배포 검증 → 이미지
  발행 → 배포 → 릴리스 태그 의존 관계도 확인했다.
- CD의 실제 shell을 사용해 다른 환경·커밋의 HTML과 다른 버전·커밋의 이미지를
  거부하는지 확인했다. 로컬 압축·복원으로 빌드 아티팩트 디렉터리 구조를 검증했다.
  GitHub의 실제 업로드·다운로드, GHCR 발행, Sentry 업로드와 원격 배포는 실행하지 않았다.
- `actionlint` 1.7.12 검사 통과. 도구가 지원하지 않는 기존 `concurrency.queue: max`
  항목의 오류만 제외했으며 해당 설정은 변경하지 않았다.

## 변경 후 비교 방법

프론트 검사를 생략한 실행, 실패·취소·재시도 실행을 성공 실행과 섞지 않는다.
CI와 개발 CD 각각 비교 가능한 성공 실행을 최소 3회 모아 다음 항목을 기록한다.

- 실행 URL, 커밋, 러너·아키텍처, 캐시 적중 여부, 실행·job·단계별 시작/종료 시각.
- 전체 시간과 러너 대기를 분리한 중앙값. 병렬 job 시간 합계는 전체 실행 시간과
  다르므로 별도로 기록하고, 러너 사용량 증가 여부도 확인한다.
- 같은 테스트 범위의 통과 여부, `Frontend checks`의 실패 차단과 프론트 변경 없는
  PR의 통과, 이미지 발행·배포 전 두 검사 성공 여부.

실행·job·단계 시각은 `gh run view RUN_ID --json jobs,createdAt,startedAt,updatedAt`
으로 조회한다. 전체 CI/CD 변경 후 수치는 GitHub Actions에서 실행한 뒤 추가한다.
