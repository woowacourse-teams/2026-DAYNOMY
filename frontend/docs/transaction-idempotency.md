# 회원 단건 거래 등록의 제출 키

V1/V2 서버 계약은 `backend/docs/adr/261124-거래 등록 멱등성.md`를 따른다. 이 문서는 해당 키를 실제 회원 화면에서 사용하기 위한 클라이언트 연결을 설명한다. 비회원 원장, CSV, 거래 수정·삭제는 대상이 아니다.

회원 화면의 단건 거래 등록은 `POST /api/v2/users/me/portfolio/transactions`를 사용한다. 거래 조회·수정·삭제·가져오기 경로는 이번 변경에 포함하지 않는다.

## 사용자 흐름

- 제출 작업을 시작할 때 UUID를 한 번 생성하고 `Idempotency-Key` 헤더로 보낸다.
- 처리 중 중복 제출은 에디터의 동기 ref 및 요청 Promise 공유로 막는다.
- 응답 유실·서버 오류·잠금 대기·인증 오류·읽을 수 없는 성공 응답은 기존 키를 유지한다.
- 미확정 거래가 있을 때 내용을 바꾸거나 다른 거래를 등록하지 않는다. 먼저 `이전 거래 결과 확인`으로 최초 본문과 키를 재전송한다.
- 성공 후에는 키를 비우고, 같은 내용의 새로운 매수도 새 키로 등록한다.
- 재응답은 최초 보유 스냅샷이므로 성공 뒤 최신 보유자산을 다시 조회한다.
- 확정적인 입력/업무 거절은 기존 작업을 종료해 내용을 수정할 수 있다. 401/403/408/409/429 및5xx는 이 분류에서 제외한다.

## 보관 범위

회원 ID로 분리한 `sessionStorage`에 키와 미확정 거래 입력만 보관한다. 인증 토큰은 저장하지 않는다. 페이지를 다시 열어도 같은 탭·회원이면 명시적인 결과 확인이 가능하다. 자동으로 거래를 재제출하지 않는다. 보관 실패는 첫 요청을 보내기 전에 오류로 처리한다. 읽을 수 없는 기존 기록은 새 키로 덮어쓰지 않는다.

탭을 닫거나 브라우저 저장소를 지운 경우, 다른 기기·새 탭에서는 이 작업 정보가 복구되지 않는다. 이 범위까지 보호하려면 서버의 미확정 작업 조회 등 별도 계약이 필요하다. 회원 ID가 없는 독립 임베딩/테스트에서는 메모리에만 보관하므로 새로고침 복구가 보장되지 않는다. 실제 앱은 AuthProvider의 회원 ID를 사용한다.

## 검증

- 단위/화면: 같은 키 유지, 성공 후 키 교체, 입력 변경 차단, 회원 분리, 오류별 키 수명, 저장 실패 전송 차단. 화면 테스트에서 저장 후 응답 유실 → 컴포넌트 재생성 → 같은 키 재확인 → 새 매수의 새 키를 검증한다. 이 화면 테스트의 서버는 mock이다.
- GitHub `Portfolio idempotency integration`: 실제 Spring Boot JAR·PostgreSQL16·Chromium을 사용한다. upstream201 뒤 브라우저 응답을 끊고, 새로고침 후 같은 키로 재확인하여 실제 이력·보유·요청기록1건을 대조한다. 이후 새 작업은2건이 되어야 한다.
- 같은 CI에서 브라우저를 닫은 뒤 API 직접 호출로 키 없는 신규/키 있는 신규/완료 재시도 각20개를 측정한다. `pg_stat_statements`로 SQL 호출 수를 집계한다. 실행 결과는 `portfolio-idempotency-integration` artifact의 `actual-api-cost.json`에 저장한다.
- 이 수치는 로컬 CI 환경의 실측이며 개발/운영 서버의 응답시간이나 처리량으로 일반화하지 않는다. CI의 통합 테스트는 앱/DB 재시작을 수행하지 않는다. 재시작·강제종료 저장소 비교 실험은 별도 개인 실험이다.

## 개발 배포

변경은 먼저 PR의 백엔드·프론트·통합 CI를 통과해야 한다. 보류한 GC 최적화는 이 PR에 포함하지 않는다. 개발 배포 중인 다른 변경을 덮어쓰지 않으며, 실제 개발 서버 검증과 CI 결과를 구분해 기록한다. 운영 배포는 범위 밖이다.
